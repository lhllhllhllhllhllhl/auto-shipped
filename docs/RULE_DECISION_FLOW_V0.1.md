# 尚舆订单完整规则判断流程 V0.1

状态：讨论稿，规则先行，尚未全部接入代码  
整理日期：2026-09-29  
关联文档：[订单自动化规则说明](ORDER_AUTOMATION_RULES_V0.1.md)｜[规则来源台账](RULE_SOURCE_LEDGER.md)

## 1. 核心结论

系统不是简单地固定执行“先判断平台，再判断公司”。这里存在两种平台概念：

- 来源平台或渠道：淘宝、天猫、京东、SAM、小红书、百礼汇等，描述订单从哪里来。
- 目标平台：管易等，描述订单最终要导入哪里。

正确做法是先联合识别“来源平台或渠道、来源公司、订单类型和用途”，形成唯一的来源配置，再通过路由表决定目标平台。

```text
原始文件或后台订单
    ↓
识别来源证据：平台／公司／文件格式／订单类型／用途
    ↓
唯一来源配置 SourceProfile
    ↓
显式路由 RouteDecision
    ↓
目标平台，例如管易
```

当Excel明确写了平台时，可以先用平台缩小范围；当Excel没有平台字段时，必须结合公司格式或用户提示，不能由AI猜测。

## 2. 完整主流程

```text
1. 接收文件或调用来源连接器
        ↓
2. 文件安全检查与批次拆分
        ↓
3. 收集来源证据
        ↓
4. 判断用途：发货、采购入库还是不明确
        ↓
5. 识别来源平台／公司／订单类型
        ↓
6. 来源是否唯一且高置信？
   ├─ 否 → Agent追问 → 等待用户补充 → 重新识别
   └─ 是
        ↓
7. 根据来源配置路由到目标平台
        ↓
8. 来源解析器生成统一订单模型 ParsedOrder
        ↓
9. 校验收件、商品、数量和一单多行关系
        ↓
10. 商品精确映射到目标平台商品与规格
        ↓
11. 生成目标平台基础字段
        ↓
12. 执行订单级策略：物流、白标、备注等
        ↓
13. 业务规则覆盖门禁
   ├─ 有待定或未实现规则 → 追问或阻断
   └─ 全部通过
        ↓
14. 生成管易Excel并执行上传前预检
        ↓
15. 当次上传授权门禁
        ↓
16. 管易待审核导入、任务中心核验
        ↓
17. 独立的审核、发货和百礼汇回填流程
```

## 3. 第一层：输入与批次判断

### 3.1 输入类型

系统接受两类输入：

1. 员工上传的公司原始Excel。
2. 已授权来源连接器取得的订单，例如未来的百礼汇后台连接器。

一次收到多个文件时逐个识别和处理，不把不同来源自动合并成同一批次。

### 3.2 文件检查

在识别业务内容前检查：

- 文件存在且可读。
- 文件类型受支持。
- 工作簿和工作表能够打开。
- 文件指纹已计算。
- 原始文件不被修改或覆盖。
- 同一批次不存在重复文件。

失败时返回技术错误，不进入业务推理。

## 4. 第二层：来源识别

### 4.1 来源识别结果

来源识别不只输出公司名称，而是输出一组结构化结果：

```text
source_system       来源系统或渠道
source_company      来源公司
source_channel      淘宝／企业店／SAM／小红书等
order_type          仓库订单／寄样／代发／地址清单等
purpose             发货／采购入库／不明确
source_profile_id   具体来源配置版本
confidence          high／medium／low
evidence            命中的工作表、表头、字段和用户提示
```

### 4.2 证据优先级

来源判断按以下优先级进行：

1. 专用连接器身份，例如百礼汇后台连接器。
2. 用户在本次提交中明确给出的平台、公司或订单类型。
3. Excel中的稳定平台字段、公司字段和订单类型字段。
4. 已登记的工作表名称、表头组合和稳定结构。
5. 文件名、商品名称和备注只能作为辅助证据。
6. AI相似度只能形成候选，不能直接确定来源。

如果用户提示与文件稳定字段冲突，系统停止并把冲突展示给用户，不能静默选择其中一个。

### 4.3 当前来源分支

| 来源 | 判断方式 | 目标处理 |
| --- | --- | --- |
| 恬田 | `仓库订单`格式加公司级证据；当前为渠道名称精确值，缺失时由用户显式确认 | 路由到管易 |
| 玉米入仓订单 | 采购订单结构、商品和订货数量 | 先追问用途；确认入库则退出发货链路 |

| 玉米地址清单 | 收件人、电话、街道、详细地址、备注 | 缺商品、数量和单号时阻断 |

### 4.4 用途分支

```text
用途=发货
    → 继续来源解析

用途=采购或入库
    → 标记为非发货资料并结束

用途不明确
    → 先问批次用途
    → 不立即逐行追问收件信息
```

## 5. 第三层：显式路由

来源识别完成后才执行路由。路由必须来自版本化配置，不由AI每次重新决定。

```text
(source_profile_id, order_type)
    → route_id
    → target_platform
    → target_profile_id
    → platform_rules_profile_id
```

当前路由状态：

| 来源 | 目标平台 | 状态 |
| --- | --- | --- |
| 恬田仓库订单 | 管易自定义订单导入 | 已确认 |
| 百礼汇代发订单 | 管易自定义订单导入 | 路由已确认，连接器待实现 |
| 玉米入仓订单 | 无默认发货路由 | 运行时追问 |
| 小红书、地址清单 | 候选为管易 | 待确认 |
| SAM、NDD、荣之达 | 管易 | 已启用生成Excel测试 |
| 孚泽 | 管易 | 待样本后启用 |
| 淘宝、企业店、日货定制、天猫、京东 | 管易 | 手工规则已知，自动来源配置待样本 |

## 6. 第四层：来源解析与统一订单模型

来源解析器只提取原订单事实：

- 来源单号、时间和来源备注。
- 收件人、联系方式和地址。
- 来源商品代码、名称、规格、数量和单位。
- 来源明确给出的金额、物流公司和物流单号；物流公司仍需经过目标平台标准名称映射，不能原样直通。
- 来源特有但需要保留的信息进入 `source_extensions`。

解析器不决定：

- 管易店铺、仓库和支付方式。
- 管易商品代码和规格代码。
- 管易平台单号生成结果。
- 最终物流和卖家备注。

### 6.1 解析校验

进入下一步前必须满足：

- 每个订单有稳定内部键。
- 一单多行能够正确分组。
- 收件人姓名存在。
- 手机或电话至少一个。
- 完整地址存在。
- 每个商品有来源编码或名称。
- 数量大于0。
- 同一订单的收件字段不存在冲突。

缺失或冲突时返回结构化追问，不生成占位值。

## 7. 第五层：商品映射

商品映射发生在统一模型之后、白标和重量规则之前。

判断顺序：

1. `来源配置 + 标识类型 + 来源编码`是否命中已确认精确映射。
2. 未命中编码时，是否命中该来源已确认的名称别名。
3. 仍未命中时，标准化商品名称和规格是否对管易商品资料形成唯一精确匹配；唯一时可以确定性通过。
4. 名称相似但不精确、或者命中多个规格时，只生成候选并让用户确认。
5. 用户确认后区分“仅本次使用”和“以后沿用”；只有明确选择以后沿用才提交飞书个人待确认映射。
6. 新映射先提交飞书个人待确认Sheet；所有者发布器全局查重并校验冲突，只有发布到正式映射表并同步为本机快照后才参与日常转换，本机旧映射不再自动加载。
7. 一个来源标识命中多个不同管易商品时立即阻断。

输出至少包含：

- 管易商品代码。
- 管易规格代码。
- 规格名称。
- 映射版本和证据。

商品映射完成后，白标库、商品重量库等产品策略才能使用稳定编码判断。

文字订单在商品映射前先执行包装语义解析。数量和包装必须分开：RZD的`根`表示彩袋单棒装，自营的`袋`表示8棒家庭装；公司第一次出现未登记的`根/袋/盒/份/套`时先追问。用户确认以后沿用时只写入本机待登记提案，所有者审核并发布正式库后其他用户才复用。黄糯、花糯、白糯裸棒属于试吃商品，普通发货在编码、名称和语义三个入口均阻断。

## 8. 第六层：管易基础字段规则

### 8.1 店铺

店铺由来源规则包中的已确认商品编码、订单类型和显式来源证据决定，不从商品名称猜测，也不把来源公司直接等同于店铺。

| 来源或类型 | 店铺 |
| --- | --- |
| 淘宝、企业店KQYD、日货定制 | 淘橘子 |
| 玉米订单 | 光明满元气 |
| SAM | sam |
| 百礼汇 | 百礼汇 |
| 天猫 | MANYANGCHI旗舰店（天猫） |
| 京东 | MAN YUAN QI旗舰店（京东） |

来源无法确定时，店铺规则不执行。

恬田、NDD和荣之达共同引用`store.corn_to_guangming_manyuanqi.v1`：商品完成确定性映射后，已确认玉米进入“光明满元气”。非玉米、商品未完成映射、一个商品命中多个店铺，或一单商品被分配到不同店铺时，系统停止并追问，不自动拆单。自营天猫/京东店铺仍由自营渠道规则决定，不使用该模块。

### 8.2 平台单号

判断顺序：

1. 该来源是否规定在来源单号基础上增加公司前缀，或生成已确认的时间序号；机器人尾缀不在这里决定，由管易公共平台层统一追加`A`。
2. 如果没有来源单号，是否存在已确认的前缀、时间粒度、时区、序号和占号范围规则。
3. 生成结果是否在本批次和管易目标范围内唯一。
4. 同一订单的所有商品行是否使用同一个平台单号。
5. 失败重跑时是否复用原编号，避免产生重复订单。

平台单号尾号的业务目的已经确认是避免重复和方便查找，顺序本身不重要，可以使用更多数字或字母。但自动化必须冻结确定性格式和并发占号方式。

公司前缀和基础编号策略属于来源级平台规则；机器人尾缀`A`属于管易公共平台规则。新增公司只配置基础编号，不在公共总控里增加公司判断分支，也不重复声明`A`。

### 8.3 其他基础字段

平台规则包按来源生成：

- 买家会员：普通来源固定为`张`；SAM按`sam+商品类型缩写+上海时区当日YYMMDD+_+跟团号`生成，当前`YM=玉米`、`SH=尚和手套`，缺跟团号、未知类型或一单多类型时追问。
- 支付金额、价格和运费。
- 仓库。
- 支付方式。
- 订单类型。
- 是否赠品、手机订单、货到付款和分销商订单。

来源规则没有明确值时，不允许把其他公司的默认值直接复用。

## 9. 第七层：订单级策略

### 9.1 物流判断

```text
原始订单是否明确指定物流？
  ├─ 是 → 校验物流名称后采用指定物流
  └─ 否
       ↓
  当前包装规则是否命中？
  ├─ 8棒家庭装合计≥2件 → 中通快递（重货）
  ├─ 已确认映射的玉米10根/10棒礼盒≥1件 → 中通快递（重货）
  └─ 否 → 韵达快递
```

当前可执行但不能推广成通用重量公式的包装规则：

- 10根玉米礼盒走中通重货。
- 8根装达到2袋，即16根，走中通重货。

尚舆自营规则包有一个来源级例外：文字明确为`京东中通`且公司已确认是尚舆自营时，渠道为京东旗舰店，物流公司直接填写`京东中通`。该值是来源明确指定的物流，因此优先于上述包装默认值；只有“京东”而没有自营公司证据时仍应追问，不能靠平台词自动套用。

同一分支还执行公司专属联系方式尾码策略：从收货人姓名末尾提取四位数字，联系电话和联系手机统一输出为`原号码-四位码`；地址末尾如有四位码则必须一致。姓名缺码、交叉核验冲突或已有号码尾码不一致时停止并追问。此策略位于自营规则包，不进入跨公司共享联系方式规则。

后续重量策略待定：

- 重货重量阈值和计算公式。
- 商品净重、包装重和计费重来源。
- 一单多商品是否按整单总重量判断。
- 其他包装组合如何计算。

当前恬田MVP可以按上述包装规则执行。取得ROY确认的重量公式后，仅替换物流策略，不修改来源解析、商品映射或模板渲染。

### 9.2 白标判断

白标判断必须在商品映射之后执行：

```text
遍历订单内已映射的管易商品和规格
    ↓
使用 product_code + spec_code 精确查询白标SKU库
    ↓
任意一件命中？
  ├─ 否 → 不添加白标提示
  └─ 是 → 整单 white_label_required=true
             → 卖家备注追加“白标商品”
```

白标库位于 `config/catalog/white_label_skus_v1.json`，当前包含：

- `SWHL3627 / 4901792023627`。
- `SWHL3610 / 4901792023610`。
- `SWHL3603 / 4901792023603`。

白标库是独立模块。增删SKU只修改新版本库，不修改来源解析器、商品映射器和Excel渲染器。

### 9.3 备注分流与卖家备注

当前规则：

1. 原始备注先进入共享备注分流模块。
2. `送货上门`、`不准放门口`、驿站/快递柜/联系收件人等明确给快递员的配送指令，统一追加到收货地址末尾并用中文括号包裹。
3. 地址已包含相同指令时不重复追加。
4. 分流后的非快递员备注进入卖家备注。
5. 白标等系统业务提示追加到卖家备注，多项使用中文分号`；`连接并精确去重。
6. 混合备注按分隔符拆分，例如`抓紧发货；不准放门口`生成卖家备注`抓紧发货`，地址末尾追加`（不准放门口）`。
7. 只有结构化规则已经执行并验证成功时，才可以不重复保留对应操作指令。
8. 商品替换等高风险自由文本不能由AI自行执行，必须匹配明确规则或追问。

## 10. 第八层：业务规则覆盖门禁

生成Excel前，对当前来源适用的全部规则逐项检查：

| 状态 | 处理 |
| --- | --- |
| 已确认且已实现 | 通过 |
| 已确认但未实现 | 阻断 |
| 待确认 | 阻断并追问 |
| 部分实现 | 阻断 |
| 已确认不适用 | 跳过 |
| 缺少规则声明 | 阻断 |

门禁检查的不是“代码有没有报错”，而是“本来源需要的业务规则是否全部有结论、有实现、有证据”。

## 11. 第九层：管易Excel生成与预检

门禁通过后：

1. 生成管易订单草稿。
2. 执行目标平台字段校验。
3. 复制48列官方模板。
4. 删除示例行。
5. 每个商品输出一行，同一订单重复订单级字段。
6. 校验必填字段、数量、金额、平台单号一致性和商品行数。
7. 生成不含收件隐私的上传预检manifest。
8. 用路径、大小和SHA-256绑定Excel与本次操作。

模板渲染器只写已经确定的值，不再执行公司识别、商品推理、物流判断或备注推理。

## 12. 第十层：浏览器上传与结果核验

浏览器上传不是与Excel转换同时上线的功能。它受独立的业务验收门禁控制。

### 12.0 分阶段发布门禁

```text
阶段A：规则与样本测试
    ↓
阶段B：只生成管易Excel，员工真实核对
    ↓
员工手工上传生成文件并验证管易结果
    ↓
转换阶段业务验收通过？
  ├─ 否 → 修正规则或转换模块，继续保持自动上传关闭
  └─ 是 → 才进入阶段C：自动化上传受控测试
```

#### 阶段A：离线规则测试

- 使用脱敏或受控样本验证来源识别、解析、路由和商品映射。
- 验证每条适用规则的来源和状态。
- 所有待确认规则继续阻断。
- 不登录管易，不选择文件。

#### 阶段B：管易Excel真实业务验收

Agent只输出：

- 管易自定义订单导入Excel。
- 不含收件隐私的预检manifest。
- 来源识别、订单数、商品行数和待确认项摘要。

员工负责：

1. 对照原始Excel检查订单数和商品数量。
2. 检查店铺、平台单号、买家会员、金额、仓库和订单类型。
3. 检查商品代码与规格代码。
4. 检查收件信息、物流、白标和卖家备注。
5. 由员工手工把生成Excel导入管易。
6. 检查任务中心结果和待审核订单内容。
7. 记录测试文件哈希、测试日期、结果和发现的问题。

每批测试使用[管易Excel转换真实测试记录](CONVERSION_TEST_RECORD_TEMPLATE.md)，不得在记录中复制收件隐私。

阶段B验收标准：

- 生成文件与原始订单逐单对账一致。
- 管易模板和必填字段通过。
- 手工导入没有字段识别错误。
- 管易订单数量和商品明细一致。
- 没有错误店铺、错误商品、错误物流或错误备注。
- 失败样本已回归测试。
- 业务负责人明确确认“转换模块通过”。

阶段B没有通过时，只修正规则、来源适配器、商品映射、平台规则或渲染器。不得用浏览器自动化绕过转换问题。

#### 阶段C：自动化上传受控测试

只有阶段B通过后才启用：

- 专用浏览器登录和短信交接。
- 自动导航到自定义导入。
- 设置待审核和两项附加选项。
- 上传前任务中心基线。
- manifest和Excel哈希复核。
- 当次授权后的文件选择。
- 将来单独授权的“确定”提交。
- 唯一新增任务核验和防重复。

自动上传测试仍不自动审核和发货。

### 12.1 上传前

- 登录或复用管易专用持久会话。
- 短信验证需要用户当次配合。
- 导航到订单导入 → 自定义导入。
- 订单状态选择待审核。
- 两项附加选项都勾选并回读。
- 建立任务中心上传前基线。
- 再次校验manifest和Excel哈希。

### 12.2 写入边界

- 文件选择需要本次明确授权。
- 点击“确定”是独立写入权限，当前尚未启用。
- 写请求发出或可能发出后禁止盲目重试。
- 必须先查询任务中心，核验唯一新增任务。

### 12.3 上传后

- 导入成功只代表创建了待审核订单。
- 自动审核尚未启用。
- 发货和物流回填是独立后续模块。
- 百礼汇物流回填必须在管易物流产生后单独执行。

## 14. 规则优先级总表

| 决策对象 | 优先级 |
| --- | --- |
| 来源身份 | 专用连接器 > 用户显式提示 > Excel稳定字段 > 已登记结构 > 辅助候选；无法唯一则追问 |
| 目标平台 | 版本化路由表；不由AI临场选择 |
| 店铺 | 公司规则包引用的共享商品策略，或公司特有的显式渠道策略；未命中和多店铺必须追问 |
| 平台单号 | 来源原单号规则 > 已确认的确定性生成规则；必须唯一且可重跑复用 |
| 商品 | 已确认编码映射 > 已确认别名；名称相似只能形成候选 |
| 物流 | 原表指定物流 > 当前已确认包装规则 > 默认韵达；未来重量规则替换策略模块 |
| 白标 | 商品映射后精确SKU库；任一商品命中则整单标记 |
| 卖家备注 | 来源客户备注 + 已确认系统提示，按固定顺序拼接并去重 |
| 仓库 | 管易来源规则包；原表仓库只作为来源事实，不直接覆盖 |
| 不确定项 | 追问或阻断，不使用临时默认值 |

## 16. 可执行伪代码

```text
process(input, user_context):
    file = inspect_input(input)
    evidence = collect_source_evidence(file, user_context)
    detection = identify_source(evidence)

    if detection.purpose == UNKNOWN:
        return needs_input(purpose_question)
    if detection.purpose == INBOUND:
        return not_a_shipping_order
    if detection.confidence != HIGH or not detection.unique:
        return needs_input(source_question)

    route = resolve_explicit_route(detection.profile_id, detection.order_type)
    parsed_orders = route.adapter.parse(file)
    validate_source_facts(parsed_orders)

    mapped_orders = exact_product_mapping(parsed_orders, route.target_platform)
    if mapped_orders.has_unconfirmed_mapping:
        return needs_input(product_mapping_question)

    drafts = apply_platform_base_rules(mapped_orders, route.rule_profile)

    for order in drafts:
        order.logistics = resolve_source_specified_logistics(order)
        if not order.logistics:
            order.logistics = resolve_confirmed_weight_rule(order)

        order.white_label_required = white_label_library.any_match(order.items)
        order.seller_remark = compose_seller_remark(
            order.source_note,
            "白标商品" if order.white_label_required else null
        )

    coverage = audit_all_applicable_rules(detection, route, drafts)
    if not coverage.passed:
        return needs_input_or_blocked(coverage.issues)

    excel = render_official_template(drafts)
    manifest = preflight_and_hash(excel)
    return ready(excel, manifest)
```

## 17. V0.1结论

系统的真实判断顺序是：先用证据联合识别来源，再路由目标平台；解析成统一事实后，先完成商品精确映射，再执行平台基础字段、物流、白标和备注等订单级规则；最后由覆盖门禁决定能否生成和上传。

白标不是来源识别规则，而是商品映射后的订单策略。公司规则不是一个大脚本，而是来源识别、字段解析、商品映射、平台字段和订单策略几个可独立替换的模块。
