# 尚舆订单规则来源台账

状态：V0.1，随规则讨论持续更新  
建立日期：2026-09-29  
关联文档：[尚舆订单自动化规则说明 V0.1](ORDER_AUTOMATION_RULES_V0.1.md)

## 1. 目的

本台账解决两个问题：

1. 对话变长或被压缩后，仍能知道每条规则来自哪里。
2. 规则接入配置和代码时，能够核验原始文件、用户确认和页面证据，而不是依赖记忆。

规则文档负责解释业务；本台账负责保存证据索引和追溯关系。

## 2. 强制追溯规则

- 每份来源资料分配稳定的 `source_id`。
- 文件证据必须记录文件名、SHA-256、页码或工作表范围。
- 用户口头或对话确认必须写入“决策记录”，不能只留在聊天上下文中。
- 同一条规则可以有多个证据，但必须区分“直接支持”“部分支持”“样本推断”和“系统设计”。
- 当前代码行为不能单独证明业务规则正确。
- 规则含义改变时直接更新当前决策记录；旧版本由Git提交历史保存。
- V1.0冻结后，机器规则必须同时记录规则编号、来源ID、确认状态、确认日期和实现引用。
- 含账号、密码、手机号、姓名或详细地址的原件不得复制进Skill、普通代码仓库或处理报告。

## 8. 原件归档风险

现在已经做到“规则来源可追溯”，但还没有完全做到“原始证据可跨电脑恢复”。原因是：

- PDF和订单样本目前主要位于本机Downloads。
- PDF包含登录信息，订单样本包含收件隐私，不能直接打包进Skill。
- 文件名和SHA-256能证明以后拿到的文件是不是同一份，但不能替代原文件本身。

V1.0冻结前需要选择一个受控归档位置，例如公司权限受控的飞书云盘文件夹。届时只在本台账记录安全归档引用，不在规则文档公开分享链接，也不把凭证写进Skill。

建议归档要求：

1. 原件只允许内部授权人员访问。
2. 每份文件保留原文件名、SHA-256、上传日期和负责人。
3. 新版本不得覆盖旧版本；使用新 `source_id` 或版本号。
4. 删除或脱敏必须形成新文件并记录新SHA-256。
5. Skill迁移只携带规则、脱敏摘要和必要的安全模板快照，不携带收件人订单原件。

## 9. 更新协议

每次用户确认一条规则时：

1. 在本台账新增或更新决策记录。
2. 在“规则与证据对照”中关联该 `decision_id`。
3. 更新主规则文档中的业务状态。
4. 规则冻结后，再更新机器规则配置。
5. 最后补充实现引用和测试证据。

任何一步缺失，都不能把规则状态标记为“已确认且已实现”。
