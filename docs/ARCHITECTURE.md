# 尚舆订单转换 Skill 架构

状态：恬田、SAM、NDD、自营文字单和荣之达文字单的管易Excel转换链路已实现；自动上传仍受独立门禁控制。

业务规则讨论稿见 [ORDER_AUTOMATION_RULES_V0.1.md](ORDER_AUTOMATION_RULES_V0.1.md)，完整规则判断流程见 [RULE_DECISION_FLOW_V0.1.md](RULE_DECISION_FLOW_V0.1.md)，规则的唯一权威结构见 [RULE_MODULE_STRUCTURE.md](RULE_MODULE_STRUCTURE.md)，AI维护入口见 [MODULE_GOVERNANCE.md](MODULE_GOVERNANCE.md)，规则来源和证据追溯见 [RULE_SOURCE_LEDGER.md](RULE_SOURCE_LEDGER.md)。架构文档不替代业务规则和来源台账。

## 1. 目标与边界

这个项目最终以一个 Agent Skill 入口提供给员工使用。普通来源由员工把原始 Excel 交给 Agent；百礼汇来源由独立连接器从其专用后台取得订单。两类来源都由 Skill 调用确定性脚本完成识别、路由、转换和校验，再由 Agent 返回可以上传的平台文件。

第一版不建设网页上传入口、用户系统、数据库或长期订单中心。Agent 已经负责文件接收与结果交付。转换过程默认不登录平台、不上传订单，也不长期保存收件人信息。

## 2. 运行主流程

```text
Agent 接收一个或多个 Excel，或调用已授权的后台来源连接器
        |
        v
来源检查与识别
        |
        v
是否命中已登记模板？-- 是 --> 确定性来源适配器（脚本快线）
        |
       否
        |
        v
用户是否明确公司？-- 否 --> Agent追问公司和用途
        |
       是
        |
        v
无数据值结构探针 -> 一次性自适应字段计划 -> 必要信息追问
        |
        v
信息是否足够？-- 否 --> Agent 提出具体问题并等待回答
        |
       是
        |
        v
公司库：确认稳定公司ID、来源归属和已启用工作流
        |
        v
路由解析：来源配置 -> 目标平台流程
        |
        v
确定性文件适配器、自适应计划解析器或后台连接器 -> 最小中间订单 ParsedOrder
        |
        v
目标平台包
  - 已确认组合商品展开
  - 平台商品映射
  - 平台业务规则
  - 平台字段校验
  - 官方模板渲染
        |
        v
管易可上传 Excel + 非敏感处理报告
        |
        v
Agent 返回结果；识别、用途或字段不确定时停止并追问
```

识别和路由发生在平台规则之前。公司身份与Excel格式分别处理：公司决定复用哪个已确认业务工作流，文件格式只决定如何抽取来源事实。平台商品编码、店铺、仓库、支付方式、平台单号生成方式和模板列都不进入公共中间模型。

## 3. 模块边界

### 3.1 Skill 调度层

职责：

- 找到用户提供的 Excel 文件。
- 调用统一转换命令。
- 在识别不确定或规则缺失时向用户说明问题。
- 返回生成文件和简短结果。

不负责：

- 临场推断订单字段值。
- 在 `SKILL.md` 中保存公司业务规则。
- 未经明确授权登录或提交平台。

### 3.2 工作簿检查与来源识别

输入：本地 Excel 文件路径。

检查：

- 文件类型和工作簿是否可读。
- 工作表名称。
- 表头所在行与表头集合。
- 必需列、可选列和稳定特征。
- 格式指纹与公司指纹分别判断；通用表头不能单独证明公司身份。
- 未登记的新列进入 `schema_warnings`，必需列缺失继续阻断。
- 是否同时匹配多个来源配置。

输出 `DetectionResult`：

```json
{
  "source_profile_id": "tiantian_warehouse_v2",
  "source_label": "恬田代发仓",
  "order_type": "warehouse_order",
  "confidence": "high",
  "matched_features": ["sheet:仓库订单", "header:来源单号", "company_column:仓库订单!渠道名称"],
  "schema_warnings": [],
  "issues": []
}
```

规则：

- `high` 才允许自动继续。
- `medium` 或多个配置并列时，Agent 必须让用户确认。
- `low` 或没有匹配时停止，不选择最相似的配置继续转换。
- 用户明确提供公司且文件命中该公司的已登记模板时走脚本快线。
- 用户明确提供公司但没有命中已登记模板时：固定工作流公司进入其自适应通道；`fallback_enabled`公司进入共享兜底的自适应通道，不再把固定模板ID当作公司ID强行校验。
- 只有格式匹配、没有公司字段或稳定位置证据时返回 `COMPANY_IDENTITY_UNCONFIRMED`。

### 3.2.1 自适应来源通道

自适应通道只服务于公司库中已经登记，并且拥有固定工作流或显式`generic_fallback`绑定的公司。固定模板优先；共享兜底不创造公司专属规则，也不直接生成平台Excel。

流程：

1. 结构探针读取工作表、候选表头、列字母、非空数量和数据类型；不返回任何数据行值。
2. Agent或确定性别名表生成一次性字段计划，把来源列映射到`ParsedOrder`字段。
3. 计划绑定来源文件SHA-256、表头签名、公司ID和复用的业务规则来源配置；任一变化都重新分析。
4. 原表同时缺少订单编号和来源单号，或缺少商品、数量时返回批次级追问；只有用户确认后才允许写入批次默认值或日期顺序号。
5. 自适应解析器重新读取原文件并生成`ParsedOrder`，之后复用原公司的路由、SOP门禁、商品映射、平台规则和预检。
6. 一次性计划不自动成为永久规则。经员工核对和真实导入验收后，才能将其字段映射提升为版本化来源配置，使后续相同格式回到脚本快线。

通用兜底只复用已确认公共规则：公司简称日序号、普通买家会员、公共金额默认值、来源物流优先和备注分流。店铺先按稳定`company_id`查正式SKU—店铺关系，再查`manual_all`；共享来源配置不作为店铺作用域。没有关系时，已映射玉米进入“光明满元气”，已映射非玉米进入“淘橘子”并在成品结果小节告知；混合店铺继续追问。固定店铺、渠道店铺和精确SKU关系始终优先，因此类别兜底不会覆盖SAM、自营天猫/京东等既有流程，也不会让不同兜底公司的店铺事实互相污染。

计划合同位于`contracts/adaptive_source_plan.schema.json`。计划只保存列映射、结构签名和经确认的批次默认值，不保存姓名、电话、地址或订单数据行。

### 3.3 追问与补充信息

订单缺少生成平台文件所需的信息时，不应直接排除文件，也不应填入猜测值。模块返回 `ClarificationRequest`，由 Agent 向用户提出具体问题。调用订单转换Skill本身已经表达“用于发货”；文件标题中的采购、入仓、备货等文字不能再单独制造用途追问。

典型例子：

```json
{
  "code": "MISSING_RECIPIENT_FIELD",
  "scope": "batch",
  "source_ref": "玉米入仓订单20260920.xlsx/Sheet1",
  "question": "文件缺少可识别的联系方式，请补充后重新提供。",
  "reason": "管易发货订单必须有有效联系方式。",
  "answer_type": "file",
  "blocking": true
}
```

处理规则：

- 先问决定后续流程的批次级问题，不要立即逐行追问缺失字段。
- 已知标签式商品表可以把页尾的统一收件人、联系方式和地址与上方多行商品组合为一张订单；未知格式由自适应结构计划复用同一解析器。
- 原表没有订单编号时，只有已登记公司简称与飞书中央日序号策略可以自动补号；没有已登记前缀时才追问。
- 回答只作为本次运行的临时补充；若要成为以后自动执行的稳定规则，必须另行更新版本化配置。
- 追问没有得到回答前，不生成标记为可上传的平台文件。

请求合同位于 `contracts/clarification_request.schema.json`。

### 3.3.1 决策收敛与待确认预览

真正缺少事实、存在多个候选、低可信唯一候选或规则冲突时继续返回`ClarificationRequest`并中途停止。候选数量与候选可信度分开判断：模糊排序必须保留名称分、规格分、综合分、候选间距及关键语义属性的命中/缺失/冲突证据；只有唯一且达到`preview_safe`的候选、跨来源完全同名且唯一指向同一正式目标的候选，或由至少两个正式SKU证明的稳定代码系列中的唯一完整规格候选，才允许转换器记录`DecisionItem`并生成`preview_ready`待确认Excel。文字/截图只缺最终人工核对时也进入该预览：

- 待确认Excel不生成上传预检manifest，浏览器模块不能接收。
- `decision_bundle`按稳定编号集中说明暂用值、判断依据及“仅本次/以后沿用”选项。
- 程序必须先生成预览Excel；聊天回复先展示`decision_bundle`，最后在“待确认 Excel”小节附上文件链接。文字入口把`masked_order_preview`作为不持久化完整隐私值的决策载荷传到结果层；员工当前订单处理对话可以从本次草稿展示完整收件值，处理报告、manifest、GitHub、反馈和长期日志仍保持脱敏。收件信息只做一次批次级核对，不得先问后生成表，也不拆成多轮逐字段确认。普通聊天文字与截图/OCR都适用；已知固定模板Excel不走该核对。
- 未明确选择`future`一律按不持久化处理；现有正式映射发生冲突时只允许本批临时处理并转管理员。
- 用户确认后由既有临时覆盖或飞书受控新增模块落地，再重新确定性转换；只有`ready`结果才生成manifest。
- 任一低可信候选存在时，整批只返回集中后的阻断问题，不生成部分Excel，也不夹带已经通过的系列候选、其他`DecisionItem`或收件信息核对；这些非阻断决策在问题解决后重跑时重新生成。阻断候选只能标记为“仅供查找”，不能描述成系统暂用值。

该模块只收敛决策，不改变公司、商品、店铺和物流规则的权威来源。合同位于`contracts/decision_bundle.schema.json`。

用户只确认候选正确、但没有选择是否长期复用时，系统先用绑定本批的临时映射生成正式成品。成功结果通过独立`mapping_reuse_bundle`保留本批实际使用的临时映射，并在成品交付后非阻断地询问“继续仅本次/以后沿用”。它不改变`ready`状态、不生成额外上传权限，也不能自行写飞书；合同位于`contracts/mapping_reuse_bundle.schema.json`。文字入口的当前批次绑定使用规范化订单事实SHA-256，与生成XLSX的ZIP时间戳无关；订单事实变化后指纹随之变化。

用户否决商品候选并提供新代码、条码、名称或规格时，不允许Agent回写来源订单字段。`product_mapping_decision`模块把用户回答绑定到原`decision_id`，从原决策包复制并哈希来源身份，再把用户原话交给目标线索解析器。解析器先查规格代码、商品代码、条码、商品名和规格名；精确结果不唯一时追问，相似结果只能继续作为候选。合同位于`contracts/product_mapping_decision.schema.json`。

### 3.4 路由解析

输入：`source_profile_id + order_type`。

输出 `RouteDecision`：

```json
{
  "route_id": "tiantian_warehouse_to_guanyi_v2",
  "target_platform": "guanyi",
  "target_profile_id": "guanyi_order_import_v1",
  "post_fulfillment_profile_id": null
}
```

路由是显式配置，不由 AI 每次重新判断。当前机器可读草案位于 `config/routing/order_routes_v1.json`。

### 3.4.1 公司注册库

公司库位于 `config/companies/company_registry_v1.json`，是各模块上方的轻量总索引。它解决“这个来源格式属于哪个公司、公司的法定名称与简称是什么、公司允许走哪些已登记工作流、目前能力做到哪一步”，但不保存店铺、物流或商品等业务值。

公司库保存：

- 稳定 `company_id`、法定名称、显示名、简称和别名。
- 该公司拥有的一个或多个来源配置。
- 来源配置到路由、目标平台规则和商品映射空间的引用。
- 转换、上传等能力的阶段状态和是否允许运行。
- 来源文档引用和最后核验日期。

公司库不保存：

- Excel列名与识别证据；这些留在 `source_profiles`。
- 字段转换、店铺、物流、备注和平台单号；这些留在 `platform_rules`。
- 商品编码对应关系；这些留在 `catalog`。
- 页面导航与写入权限；这些留在浏览器执行器。

公司法定名称与简称都可以作为公司身份提示；大小写不敏感的简称会先解析成稳定`company_id`。平台规则必须显式声明`prefix_source=company_abbreviation`或相应会员前缀引用，简称才会进入输出字段，避免所有公司被强制套用同一种单号格式。

员工交互层允许存在与“公司”同层的稳定业务来源，例如`JZDZ`和`DRJY`。这类来源不是临时标签：它们分别拥有独立`source_profile_id`、路由和规则包；底层可共同归属`self_operated`，从而复用自营默认值而不把员工入口强行描述成同一家公司。来源分类负责“这笔订单走哪条规则”，公司归属负责共享身份和能力，两者不互相替代。

转换服务会强制执行双向归属与工作流引用校验。公司未登记、一个来源同时归属多个公司、公司库与路由引用不一致、工作流未启用时均停止，不继续猜测。只有名称和简称、没有来源模板与规则的公司使用`identity_only`状态；它们可以被识别，但不能转换。`audit-companies` 可在不读取订单数据的情况下检查全部引用。

### 3.4.2 共享平台策略模块

管易跨公司的同类业务值不再复制到每个公司规则包。`config/platform_rules/guanyi/policy_modules_v1.json`是共享店铺、普通买家会员、公共默认值、物流、备注分流和卖家备注组合策略的唯一可执行权威；公司规则包通过`policy_module_refs`引用，并只保存公司专属的单号、字段显示、套餐和显式例外。给快递员的配送指令由共享备注分流模块追加到收货地址末尾，非快递员备注再进入卖家备注组合模块。

加载规则时先解析共享模块，再执行SOP覆盖门禁和转换。引用缺失、模块目标类型不匹配、覆盖格式错误，或同一个规则既内联又引用时全部fail-close。公司库审计也会验证所有活动工作流的模块引用。

### 3.4.3 用户纠错反馈箱

用户否决系统结果或人工修正成品时，Agent可以在用户确认后把非隐私事实追加到独立飞书反馈箱。反馈箱不参与订单转换，也不能覆盖正式规则。正式库缺少映射键时，完整且经用户确认以后沿用的商品映射可走受控直接新增；已有键的替换、删除或冲突只能做当前批次临时替换并转管理员。开发维护线程通过只读汇总按问题键去重，再决定修改映射、规则或代码。合同和状态边界见`docs/CORRECTION_FEEDBACK_GOVERNANCE.md`。

### 3.5 来源适配器与后台连接器

两者职责相同：

- 读取指定来源格式，或从已确认的后台接口取得订单。
- 识别一单多行并正确分组。
- 提取订单的客观事实。
- 保留原文件、工作表和行号追踪信息。
- 信息完整时输出 `ParsedOrder`；信息不足时输出 `ClarificationRequest`。

不负责：

- 决定目标平台。
- 生成平台单号。
- 选择平台店铺或仓库。
- 解析管易商品代码。
- 写入平台模板。

来源模块分为两类：

- 文件适配器：员工上传公司原始 Excel 后识别和解析。
- 后台连接器：在运行时授权范围内通过后台导出、官方 API 或已登录网页读取订单。

无论来源形式如何，输出都必须满足同一个 `ParsedOrder` 合同。账号、密码和会话信息不得写入 Skill、配置或处理报告。

### 3.6 最小中间订单

`ParsedOrder` 是来源适配器与平台包之间的稳定合同，正式草案位于 `contracts/parsed_order.schema.json`。

它只保存来源中的客观事实：

- 来源文件、工作表和行号。
- 来源公司、文件类型和来源订单号。
- 收件人、联系方式和地址。
- 来源商品、规格、数量和单位。
- 下单时间、金额和原始备注等可选事实。

它不包含：

- 管易店铺、仓库和支付方式。
- 管易商品代码或规格代码。
- 百礼汇平台字段。
- 平台单号生成结果。
- 是否可以上传等平台校验状态。

平台新增字段时先判断它是不是所有来源都可能提供的客观事实。只有满足这个条件才扩展 `ParsedOrder`；否则字段属于对应平台草稿模型。

### 3.7 目标平台包

每个平台包拥有自己的完整转换逻辑：

```text
ParsedOrder
  -> 来源组合商品展开（如适用）
  -> 平台商品解析
  -> 平台业务规则补全
  -> PlatformOrderDraft
  -> 平台校验
  -> 官方模板渲染
```

平台包内部至少分为：

- 商品映射：来源商品标识到该平台商品/规格编码。
- 组合商品展开：只对已确认的来源商品与规格执行一对多拆分，记录每个目标商品和数量倍数；未命中则继续普通一对一映射。
- 店铺路由：使用已确认的精确商品编码、订单类型或显式来源证据分配店铺；未命中或一单多店铺时阻断并追问。
- 业务规则：平台单号、仓库、状态、支付和物流等。
- 草稿模型：该平台需要的字段集合。
- 校验器：阻断缺字段、未知商品、重复单号和模板不兼容。
- 渲染器：复制官方模板后写入数据，保留工作表名称、格式和文本标识符。

#### 管易平台包

第一版统一使用管易“自定义订单导入”单文件模板，与 SOP 中 SAM 订单的自定义导入方式一致。模板包含 48 列；同一订单有多件商品时，每件商品占一行，并重复相同平台单号及订单级字段。

管易允许自定义导入增删列并调整列位置；系统仍使用已校验的官方48列模板作为稳定合同。人工文件中的“团标题”等非业务列不进入自动输出。

模板用红色表头标出的必填列是：店铺、平台单号、买家会员、支付金额、商品代码、数量、价格、收货人和收货地址。

当前模板结构已记录在 `config/platform_profiles/guanyi_order_import_v1.json`。

#### 百礼汇来源连接器

百礼汇不是订单导入目标平台，而是一个特殊订单来源。已确认的主流程是：

```text
百礼汇专用后台取单
  -> 百礼汇来源连接器
  -> ParsedOrder
  -> 百礼汇来源对应的管易商品映射与业务规则
  -> 管易自定义订单导入.xlsx
```

员工仍然只使用同一个 Skill 入口。百礼汇只替换来源模块，后面的中间合同、商品映射校验、管易规则和模板渲染全部复用。

当前还需要确认后台的实际取单方式：优先使用后台 Excel 导出，其次是官方 API；只有前两者不可用时，才在用户已登录且明确授权的会话中读取网页。相关配置位于 `config/source_connectors/bailihui_backend_v1.json`，系统能力边界记录在 `config/platform_profiles/bailihui_v1.json`。

管易产生物流后的百礼汇发货回填是另一项独立能力，不与“取单并导入管易”绑在同一个模块中；待入单闭环稳定后再实现。

### 3.9 上传前预检与批次清单

管易 Excel 渲染完成后必须再次从磁盘读取并执行上传前预检。预检属于平台包，不属于浏览器执行器，检查：

- 工作表和 48 列表头与登记模板一致。
- 至少存在一行订单明细，必填列不为空。
- 数量、金额和 0/1 标志符合类型与范围。
- 标识符列保持文本格式。
- 不包含公式或错误单元格。
- 同一平台单号的订单级字段一致。

通过后生成符合 `contracts/upload_batch.schema.json` 的 manifest。manifest 只包含文件哈希、大小、配置版本、订单数、明细行数、平台单号审核范围、检查结果和非敏感错误位置，不包含姓名、手机号或地址，也不构成上传或审核授权。平台单号只供上传后“只审核本批”绑定范围使用。

转换完成后先把 Excel、manifest 和脱敏摘要交付用户并停止；用户查看后在当前对话另行明确指定上传批次，才允许浏览器执行器继续。执行器在打开文件选择器之前必须重新计算 Excel 哈希并与 manifest 比对。manifest 缺失、状态不是 `ready`，或当前 Excel 的文件名、大小、哈希不一致时停止。manifest 中的原始路径只记录转换时的位置；跨电脑或云工作区传输后，浏览器执行器可以显式绑定用户交付的当前路径，但不得改写 manifest、扫描目录或猜测文件。即使 manifest 通过，文件选择和上传仍属于后续独立能力，需要单独的运行时授权。

### 3.10 多文件批次编排

批次编排层位于单文件转换服务之上，不复制任何公司或平台规则。统一入口收到多个原始 Excel 时默认进入合并模式；只有用户明确要求分开或分别输出时才进入单文件循环模式。合并模式依次对每个文件运行完整的“识别 → 公司库 → 路由 → 解析 → 商品映射 → 平台规则 → 渲染 → 预检”链路；单文件中间成品只写入临时目录。

只有同时满足以下条件时，批次层才把已验证的数据行按用户提供文件的顺序重新渲染成一个正式 Excel：

- 每个文件的状态均为 `ready`。
- 所有文件进入同一目标平台和同一目标模板配置。
- 原始文件内容哈希不重复。
- 不同文件之间没有相同的平台单号。
- 每个暂存 Excel 的 SHA-256 与自身预检 manifest 一致。

若没有阻断问题、但至少一个文件包含待确认决策，批次层可以合并为一个`preview_ready`预览；它集中所有决策且不生成manifest。任一文件需要追问时，整批返回 `needs_input`，不生成部分 Excel；任一文件失败、哈希异常或跨文件单号冲突时，整批返回 `blocked`。只有全部`ready`的成功批次才交付合并 Excel、manifest 和不含收件信息的批次报告。批次合并不会改变单文件的来源判断、商品映射或业务规则。

### 3.10 Agent 内的浏览器执行边界

同一 Agent、同一持续运行环境是默认部署方式：转换模块把生成的 Excel 路径和 manifest 路径直接交给浏览器执行器，不需要额外上传到另一台机器。若平台把附件复制到新的云端路径，Agent必须同时传入明确的当前 Excel 路径；执行器以原 manifest 的文件名、大小和 SHA-256 核验后建立路径绑定，并在 operation 中同时保留原始位置与当前位置。两部分仍通过 manifest 隔离：浏览器只读取 Excel 路径、SHA-256、目标平台配置、订单/行数摘要和 operation ID；不得读取原始公司订单，也不得重新判断公司、商品、白标、店铺、物流或备注。

同一对话可以先后产生多个可上传 manifest。Agent维护当前对话已知的明确批次集合，用户说“把这些都上传”时先回显所指批次，再为每个 manifest 建立独立 operation ID，按顺序执行任务基线、两段提交和任务中心结果核验。第一次确定后必须完整核对虚拟滚动字段表，第二次确定后必须以唯一新增任务 ID 关联结果；“执行完成”仍不是业务成功，只有结果汇总显示全部成功才闭环。前一批未核验成功时停止后续批次；不扫描目录或按修改时间猜测文件。

Agent 向用户返回非敏感闭环结果：operation ID、任务 ID、导入总数、成功数、失败分类、需要人工处理的来源行号和下一步建议。浏览器执行器不得把任务结果中的收件人、手机号、详细地址、原始失败行或页面响应正文写入状态、日志或对话。

上传全部成功后，订单审核由独立`order_audit`模块接管。它只接受`post_write_verified`导入操作，建立新的审核operation；当前必须由用户在上传成功后另行授权，精确口令为`CONFIRM_GUANYI_ORDER_AUDIT`，上传授权不得继承。默认范围`all_pending`会筛选订单查询页中当前全部待审核订单并按页审核；`current_batch`只在用户明确要求时使用manifest的平台单号清单。审核写请求可能发出后只允许回读剩余待审核订单，不得盲目重试。未来上传与审核连跑只能通过版本化策略切换，当前显式关闭；发货、作废和删除仍是禁止动作。真实审核在本地与豆包环境分别完成只读控件探针、并确认待审核状态词之前保持规则门禁关闭。

账号密码属于运行环境凭证，不属于 Skill 或订单数据合同。本地使用 Keychain/DPAPI；Linux/云端优先使用平台 Secret/Vault 的只读凭证助手。没有安全入口且用户明确接受对话留存风险时，现有登录 operation 可进入 `waiting_for_credentials`，通过随机令牌loopback控制通道或私有stdin把本次凭据交给worker。豆包工作Linux的Playwright worker通过loopback CDP连接平台自带浏览器，直接观察并操作同一管易页面；执行器只在内存填值，不把字段内容写入状态、文件、环境变量、命令或日志。短信验证码继续使用同一短时operation ID。单一浏览器会话锁禁止probe或第二个登录抢占当前worker。

额外安全验证采用“通用识别 + 接入策略”两层。核心只识别白名单URL，未知页面仍失败关闭。本机/独立headed浏览器可进入`waiting_for_human_verification`，保持原Playwright context/worker并把同一窗口交给当前电脑用户；窗口class/`xdotool`只属于显示适配。豆包`platform_cdp`命中阿里云验证页时不做云端交接，而以`LOGIN_LOCAL_VERIFICATION_REQUIRED`终止worker并释放锁；用户或管理员在自己的可信电脑完整登录并确认进入管易首页后，豆包只读探测并最多重试一次。两种路径都禁止盲目重登、重发短信、复制会话材料或删除profile。

Geometry Guard同样区分窗口所有权：本地持久浏览器可由执行器校准原生窗口；`platform_cdp`的外层窗口和viewport由豆包平台管理，不要求匹配本地浏览器的`1440×850`目标，执行器只读验证三次采样稳定、有效client区域和页面缩放，不调用窗口修复。平台固有的宽高滚动条沟槽还必须由document/visual证据分别一致证明、各不超过24px；否则仍然失败关闭。

## 4. 商品映射

商品映射采用公司隔离的多标识级联匹配，但由目标平台包调用：

```text
来源配置 + 标识类型 + 来源编码/名称
        -> 内部商品标识
        -> 目标平台商品代码与规格代码
```

内部商品标识只表示同一个真实商品，不保存平台业务含义。同一商品在管易和百礼汇可以映射为不同编码。

确定性优先级为：公司专属已确认编码/条码、当前来源正式名称规范身份、全局正式名称规范身份、其他来源相同规范身份候选、标准化后唯一精确的管易商品名称、正式别名建立的目标商品系列内规格候选、普通相似名称候选。文字/OCR入口保留商品原文，Agent初拆品牌、商品主体、规格、数量和单位；`product_phrase_normalizer`再根据版本化语言词典生成与字段边界无关的`品牌+商品主体+规格`身份。它不选择管易SKU、不读取目标代码，也不改变数量和单位；无法识别的附加词进入残余规格，避免被静默丢弃。当前来源或全局正式名称映射规范身份唯一相同时可直接命中；其他来源的相同身份仍只生成`preview_safe`候选。系列上下文要求同一规范商品身份至少已有两个不同的飞书正式SKU，且目标商品代码共享不少于四位字母前缀；新规格的颜色、软硬等显式属性必须在系列内完整且唯一命中。系列结果仍是待确认候选而非正式映射。名称同时命中多个规格、模糊相似或未匹配时阻断并追问。来源编码与管易编码相同也不能自动直连，除非该来源配置明确声明两个编码空间相同。

编码或条码已精确命中正式映射时，目标SKU继续以编码映射为准。来源同时提供的名称只做语义校验：词序、字段边界和已登记同义词等外观差异不提示；明显指向另一类商品时仍先生成无manifest的`preview_ready` Excel，并用`SOURCE_NAME_DIFFERS_FROM_CONFIRMED_CODE_MAPPING`要求本批确认，而不是中途改选SKU或阻断Excel。用户确认后由来源指纹绑定的当前批次覆盖消除提示；长期替换仍走管理员治理。

来源匹配政策和身份保护随 Skill 版本发布；一对一商品目标映射以飞书正式映射表为权威数据源。日常转换自动加载当次成功同步的正式快照；唯一允许的本机运行时例外是“用户否决已有正式映射”的当前批次替换记录，它同时绑定来源文件SHA-256和预期旧正式目标，其他文件或正式目标变化时自动忽略。普通本机旧映射不再隐式加载。

商品映射和目标商品目录是两个不同模块：映射回答“这个来源商品指向哪个管易商品代码/规格代码”，目录回答“这个目标代码是否存在、叫什么、有没有规格和仓库等属性”。正式映射不保存目录来源，也不因为目录分层而改变表结构。

正式名称映射除原始`source_value/source_spec`外，由程序维护`canonical_source_brand`、`canonical_source_product`、`canonical_source_spec`和`canonical_schema_version`。`product_name`行必须得到规范商品主体；品牌与规格按来源事实可空。商品代码/条码行以代码为身份，来源没有可靠名称时规范字段允许为空，禁止从目标管易商品名称反推来源身份。规范规格使用`|`分隔多个维度；该符号只表示结构边界，不是残余规格文本，规范身份重复处理必须保持幂等。运行时先兼容旧15列表并在快照中派生规范字段；迁移到19列表必须先只读计划、检查规范身份冲突，再由所有者确认写入并递增正式库版本。

已登记公司从旧专用来源入口迁移到`generic_company_manual_v1`时，历史映射不会被全局复制。公司库可在`generic_fallback.mapping_source_profile_aliases`中显式声明同公司兼容入口；运行时先查当前入口，再查声明的旧入口，并且只有所有兼容命中都指向同一目标SKU或同一组合组成时才复用。未声明入口、跨公司入口或目标冲突都失败关闭。

转换结果保留批次级`mapping_evidence`：商品原文、Agent初始拆分、规范身份、命中的映射ID、目标SKU、正式库版本与快照哈希。该证据不含收件信息，只跟随本批结果/报告，不写回Skill或正式库，因此不会随订单积累扩大运行时。

目标商品目录由`product_catalog_layers_v1`统一解析，但原始文件保持独立：

1. `business_preferred`业务优先目录先查，用于入库资料、专项商品清单等业务确认过的补充目标商品。
2. 没有高优先级候选时，再查`guanyi_master`管易商品主档。
3. 两层存在完全相同的商品代码+规格代码时，以业务优先层的名称和规格为准；其空缺的重量、仓库等属性只有在下层值一致时才补齐。
4. 高优先级目录的待补全行不参与运行；标记生效却缺少商品代码时失败关闭。
5. 运行时只做逻辑合并，不生成一个需要人工维护的物理总表。更新业务优先目录或管易主档时只替换各自快照和登记文件，另一层不动。

当前层注册表位于`config/catalog/product_catalog_layers_v1.json`。业务优先目录由`config/catalog/preferred_product_catalog.json`登记，管易主档继续由`config/catalog/current_product_catalog.json`登记。Skill入口自动加载两层；显式`--catalog`只替换本次管易主档，显式`--preferred-catalog`只替换本次业务优先目录。

组合商品展开不是普通商品映射。长期组成事实由飞书正式工作簿独立的“组合商品规则”关系表维护“公司+来源配置+来源商品+来源规格 -> 多个目标商品+数量倍数”；来源规则包只声明展开策略，避免同一事实散落多个文件。仅本次组成保存在与来源文件SHA-256绑定的临时覆盖层。展开后每个目标商品仍必须通过当前有效目标目录精确校验。禁止向普通一对一映射表写入相同来源键的多个目标商品，否则必须按冲突处理。

### 4.1 飞书共享映射治理

共享映射采用两个飞书电子表格工作簿：正式映射是权威数据源，待确认映射是非可信例外收件箱。普通Agent不能任意编辑正式表，只能通过受控命令创建一个不存在且无冲突的映射键；已有键的变更必须转管理员。

正式工作簿内部使用三张职责不同的关系表：`正式映射`保存“公司/来源的商品标识或名称别名 → 唯一管易商品+规格”，`组合商品规则`保存“一条来源商品 → 多个管易商品+数量倍数”，`手工单商品店铺`保存“来源作用域+已经规范化的管易商品+规格 → 管易店铺”。这样一对一、一对多和店铺事实不会混在同一表，也能为JZDZ、DRJY等具体来源覆盖`manual_all`通用关系。缺失、冲突或一单跨店铺时失败关闭。

待确认工作簿按当前飞书`user_id`自动路由到个人Sheet。路由表由Agent自动创建和修复；路由表缺失时通过个人Sheet的`owner_user_id`元数据重建。没有Sheet时复制模板创建；同一用户出现多个Sheet时阻断，不自动合并或删除。

飞书工具优先使用Agent原生能力，CLI只作备用。所有Python侧CLI消费者统一通过`LarkCliClient`执行命令、解析JSON和探测用户身份；商品映射与中央日序号仍是两个独立业务网关，不共享表结构或业务规则。共享身份探针依次使用`auth status`、`whoami`和用户身份`user_info`只读接口；业务网关接受身份前还必须用同一user身份读取自己的目标工作簿。不得靠Agent临时命令垫片改变运行环境。直接新增要求当前用户身份、确定性`mapping_key`、公司/来源登记、唯一目标、单写者锁、`staged`记录、`mapping_revision`原子读指针、发布日志和写后精确回读；中断时旧提交版本继续供转换使用，只暂停后续正式写入。完全重复幂等，同键不同目标阻断。待确认写入仍要求幂等`proposal_id`，所有者发布器处理全局冲突和例外。转换器本身没有正式表写权限。详细合同见`docs/FEISHU_MAPPING_GOVERNANCE.md`。

### 4.2 飞书中央日序号

缺少订单编号和来源单号的已登记文字来源，不再依赖本机分钟生成唯一号。`config/integrations/feishu_daily_sequence_v1.json`绑定独立飞书工作簿，年度页按`日序号_YYYY`滚动；一行代表一次批次区间占号，不保存收件人、电话、地址或来源文件名。

占号命名空间固定为`purpose + prefix + business_date`。不同前缀、平台单号与SAM买家会员互不污染；同一前缀即使来自不同来源配置也共享当天序号。日期变化后新命名空间从001开始，序号超过999自然扩位。幂等键由用途、来源配置、来源SHA-256和可选来源分区组成，不把可调整的前缀放进幂等身份；因此同一来源跨日或规则调整后重跑仍复用最初日期、前缀、格式和区间，订单数量变化则阻断。SAM无跟团号订单以商品类型代码作为来源分区，避免同一文件中的YM与SH互相误复用。

新占号采用“读取全部年度台账 → 计算空闲区间 → 追加 → 回读 → 检查重叠”的失败关闭协议。它与映射网关共用`LarkCliClient`的身份兼容层，并在占号前额外读取中央台账工作簿验证资源权限；因此旧版CLI缺少`auth`或`whoami`时也走同一确定性回退，不允许Agent临时造垫片。飞书不可用时，本机缓存只能复用已经完成中央写入和回读的旧分配；新批次禁止离线从001起号。旧分钟账本只保留历史复跑兼容，不再供新规则使用。

## 5. 校验分层

### 来源校验

- 工作簿可读。
- 必需工作表和表头存在。
- 一单多行的订单级字段一致。
- 数量是正数。
- 联系方式和地址没有明显缺失。

### 中间合同校验

- `ParsedOrder` 满足 JSON Schema。
- 每个订单有稳定的 `record_key` 和来源追踪信息。
- 不允许混入平台专属字段。

### 平台校验

- 平台必填字段齐全。
- 商品和规格映射已确认。
- 平台单号规则已确认且批次内不重复。
- 模板版本与平台配置一致。
- 同一订单的多行商品使用相同平台单号。
- 每个中间订单至少产生一行模板记录，模板记录数量等于全部商品明细数量。

### SOP业务规则覆盖门禁

平台字段校验只能发现“值缺失”，无法发现“SOP规则从未进入系统”。因此在商品映射和模板渲染前增加独立覆盖门禁：

- 规则目录保存稳定规则ID、来源页、模块归属和执行阶段。
- 每个来源到平台的规则包声明适用规则的状态与实现引用。
- 规则包先通过轻量核心Schema；公司新增业务字段不受限制，但身份、版本和覆盖声明不能缺失或写错类型。
- 标记为`implemented`的引用必须同时存在于实现注册表，并指向可加载代码入口和测试文件。
- `implemented` 和 `not_applicable` 必须经过确认；其他状态一律阻断对应阶段。
- 转换、上传、上传后核验和履约回填分阶段检查，避免转换阶段规则与浏览器权限耦合。
- 规则包漏掉目录要求的规则时直接返回结构化追问，不允许静默生成文件。

当前转换服务已强制执行 `conversion` 阶段；`upload` 阶段将在启用“确定”提交前接入浏览器执行器。详见 `docs/BUSINESS_RULE_COVERAGE.md`。

## 6. AI 与脚本的职责

脚本承担：

- 表头识别和确定性评分。
- 来源字段解析和订单分组。
- 路由查表。
- 商品映射、业务规则和校验。
- 平台模板写入。

Agent/AI 承担：

- 理解员工请求并选择本 Skill。
- 发现识别结果不唯一时组织人工确认。
- 解释阻断原因。
- 调用脚本并返回结果。

AI 的一次确认不能只对当前文件生效后被遗忘。确认后的稳定规则应写入新的版本化配置或适配器，并通过样本测试。

## 7. 记录与隐私

第一版不建设持久化治理系统。每次运行只产生一个非敏感处理摘要，包含：

- 输入文件名和文件指纹。
- 识别到的来源配置。
- 使用的路由和平台配置版本。
- 成功、阻断订单数量。
- 错误代码及来源行号。
- 输出文件名。
- 用户对本次运行追问的回答类型，但不记录回答中的个人信息。

处理摘要不保存姓名、手机号和详细地址。中间订单默认只在运行期间存在；除非用户明确要求调试，不落盘保存包含个人信息的中间 JSON。
