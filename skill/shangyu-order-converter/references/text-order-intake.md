# 文字与截图订单入口

当员工直接发送聊天文字、截图或复制的地址单，而不是Excel时，使用两阶段入口：Agent提取候选字段，确定性脚本校验和落地。文字识别不能绕过公司、商品、物流或平台规则。

## Agent提取

1. 从文字或截图按订单分段。截图可以由Agent视觉能力读取；不要把OCR结果当作已确认事实。
2. 生成符合`runtime/auto-shipped/contracts/text_order_draft.schema.json`的本次临时JSON。草稿可以包含收件信息，但只能保存在本次输出目录，不得进入Skill、规则文档、日志或聊天正文。
3. 对以下关键字段标注`field_provenance`：平台/渠道、来源单号、收件人、联系方式、地址、商品及数量。原文明示使用`explicit`，用户回答确认后使用`user_confirmed`；模型推断使用`inferred`，缺失使用`missing`。
4. 任何拆分歧义都放进`uncertainties`。典型歧义包括：一串数字无法确定是手机号还是订单号、未确认公司时无法判断“京东中通”的业务含义、公司尚未登记根/袋的包装含义、只有商品简称而没有唯一映射、同一段里出现多个地址。公司已确认是尚舆自营时，“京东中通”已登记为`source_channel=京东`且`source_carrier=京东中通`，不再追问。
5. 商品短语必须拆成商品主体、规格、数量和单位四类字段。例如“橘色搓澡巾1条”写为`source_product_name=搓澡巾`、`source_spec=橘色`、`quantity=1`、`unit=条`；“条”是单位，不是规格。Agent不得直接填写管易代码。若Agent仍把“橘色搓澡巾”保留为一个名称且规格为空，商品映射层只允许用飞书正式映射中已发布的“来源名称+来源规格”做正序/倒序精确组合拆分；唯一目标可继续，多个目标或没有目标仍追问，绝不使用模糊相似自动确认。
6. 玉米文字如“黄糯2根”“花糯1袋”应拆成品类、数量和原始单位：商品名称分别为“黄糯”“花糯”，数量分别为2和1，`source_spec`与`unit`分别填写“根”或“袋”。不要由Agent直接选择SKU。后续正式包装语义库会把RZD的`根`解析为彩袋单棒装、自营的`袋`解析为8棒家庭装；公司第一次出现未登记表达时追问一次。裸棒普通发货禁用。
7. 形如`13800138000-3940`的联系方式是平台隐私号整体。完整写入`recipient.contact`，不得截断尾部数字；脱敏预览仍只显示掩码。
8. 用户确认属于尚舆自营后，天猫和京东分别写入`source_channel=天猫`或`京东`，消息中的平台单号写入`source_order_no`。店铺与机器人尾缀由后续规则包处理，Agent不要在草稿里拼接店铺名或`A`。若自营京东订单明确写`京东中通`，必须保留收货人姓名末尾的四位码；可同时把提取值写入`source_extensions.jd_zto_contact_suffix`用于交叉核验，但不能用该字段代替姓名原文。地址末尾也有四位码时必须一致；缺失或冲突时写入`uncertainties`并追问，不得自行补数。转换层会把联系方式输出为`原号码-四位码`。
9. `RZD`是荣之达公司证据。没有来源单号时不要让Agent自行拼号，也不要在草稿中填`order_number_policy`；来源配置会生成`RZD+上海时区整批生成分钟YYYYMMDDHHmm+最少两位弹性序号`，公共管易层再追加`A`。同一批冻结一个分钟；本机占号记录会让同一分钟第二批续号，并使同一来源重跑复用原号。RZD的`根`表示彩袋单棒装，数量按根数原样写入；`袋`等未登记表达继续追问。玉米商品通过共享店铺模块进入“光明满元气”。当前规则按单电脑场景设计；如果用户明确要多电脑并发，必须先接入中央占号，不能声称本机记录能够跨电脑防重。
10. Agent确认内容属于非Excel订单、用户又没有指定公司或规则包时，只生成一个草稿，`company_id=null`、`rule_source_profile_id=null`；`routing_mode`可显式写`registered_manual_channels`，不写时脚本也默认采用该模式。每笔订单仍各自填写原文明示的`source_channel`。脚本会逐笔匹配已登记来源配置，按公司和规则包分组，并为每组生成独立的标准化Excel与自适应计划；随后统一批次入口默认合并为一个管易Excel。唯一命中时不增加“是否手工订单”的独立确认，脱敏订单预览确认已经覆盖本次提取和路由；未知或同时命中多个来源时只追问该笔来源。若用户已明确公司或规则包，则继续使用单一来源流程。
11. 送货上门、不准放门口、驿站/快递柜、派送联系等明确给快递员的配送指令，优先写入`source_extensions.delivery_instruction`，保留原文，不拼进地址。确定性转换层会统一追加到收货地址末尾并去重；其余来源备注继续写`source_note`。同一段同时包含配送指令和其他备注时，Agent应按语义拆开；无法可靠拆分时放入`uncertainties`追问，不得猜测。

## 校验与确认

先运行：

```bash
python3 <skill-dir>/scripts/text_order.py validate --draft <草稿.json>
```

命令只返回脱敏预览和集中追问。没有公司级证据时必须问公司；平台名称不能代替公司来源。脱敏预览中的`order_number_plan`按“订单编号 > 来源单号 > 已登记自动生成规则”说明本单将如何编号。两种单号都缺失但来源配置已有确认过的日期/分钟序号规则时，只向用户展示将采用的规则，不再要求用户补充单号或重新选择；没有已登记生成规则时才追问，且不得由Agent临时决定。

全部字段明确后，向用户展示脱敏预览，至少包含订单数、平台/渠道、商品、规格、数量和指定物流。只有用户明确确认后，才把`confirmation.token`设为`CONFIRM_TEXT_ORDER_DRAFT`。

## 生成转换输入

用户确认后运行：

```bash
python3 <skill-dir>/scripts/text_order.py prepare \
  --draft <已确认草稿.json> \
  --output-dir <本次临时目录>
```

普通单一来源命令生成一个标准化来源Excel和一个与该Excel哈希绑定的一次性自适应计划。混合手工订单会按路由组生成多组文件，并在JSON结果的`conversion_inputs`中明确给出每组的`company_id`、`rule_source_profile_id`、`source`和`adaptive_plan`，Agent必须使用这些配对，不能自行猜测。它们都不是管易成品。随后把标准化Excel和计划交给统一转换入口：

```bash
python3 <skill-dir>/scripts/convert_orders.py \
  --source <文字订单标准化.xlsx> \
  --company-hint '<文字订单标准化.xlsx>=<company_id>' \
  --adaptive-plan-hint '<文字订单标准化.xlsx>=<文字订单自适应计划.json>' \
  --output-dir <本次输出目录>
```

统一转换入口仍会执行飞书正式商品映射、公司路由、平台规则、物流规则和管易预检。未知商品或规则继续追问；不得因为用户已经确认文字识别结果就跳过业务规则确认。

多条文字订单默认合并成一个管易Excel。混合手工订单把`conversion_inputs`中的全部`source`与对应提示一次性交给统一批次入口。若用户同时提供文字单和原始Excel，可先把文字单准备为标准化来源Excel，再与其他来源一起交给统一批次入口。
