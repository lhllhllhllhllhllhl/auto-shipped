# 尚舆订单自动化规则说明 V0.1

状态：讨论稿，未冻结，暂不作为自动执行依据  
整理日期：2026-09-29  
适用范围：公司原始订单识别、统一订单模型、管易自定义订单转换、管易上传及后续核验

规则来源、文件指纹、PDF页码、样本工作表范围和用户决策记录统一维护在[规则来源台账](RULE_SOURCE_LEDGER.md)。本文件中的“PDF第几页”“样本事实”和“用户确认”都必须能回到台账中的稳定来源ID。

从订单输入到管易上传的完整判断顺序、优先级和追问分支见[完整规则判断流程](RULE_DECISION_FLOW_V0.1.md)。

2026-09-29转发的Xavier十项业务答复统一登记为 `SRC-QA-XAVIER-20260929`；其中明确表示不清楚或与PDF冲突的内容只作为待核证据，不作为最终规则。

## 1. 文档目的

这份文档先把业务规则梳理清楚，再决定哪些规则进入机器配置和代码。

V0.1 只完成以下工作：

- 汇总 PDF、样本文件和对话中已经确认的规则。
- 区分来源事实、业务规则、系统实现和待确认问题。
- 明确每条规则属于流程中的哪个模块。
- 给后续实现和验收提供一份可逐条确认的清单。

V0.1 不代表：

- 所有规则已经获得业务确认。
- 所有来源都已经可以自动转换。
- 生成的文件已经获准上传。
- 系统可以自动点击管易“确定”、审核或发货。

## 2. 规则证据与状态

### 2.1 证据类型

| 类型 | 含义 | 示例 |
| --- | --- | --- |
| PDF事实 | 《尚舆发货流程》直接写明的规则 | 玉米订单店铺选择“光明满元气” |
| 当前模板或页面事实 | 现行管易模板、当前页面真实显示的字段和选项 | 自定义订单导入模板包含48列 |
| 用户确认 | 业务负责人在对话中明确确认 | SAM日期使用上传当日日期 |
| 样本事实 | 原始Excel中可以直接观察到的信息 | 小红书样本顶部列出3个商品条码 |
| 样本推断 | 根据一个样本推测，但还不能作为长期规则 | 小红书每个地址默认发3种口味各1根 |
| 当前实现 | 代码现在的行为 | 恬田客户备注目前会复制到卖家备注 |

当前实现不是业务证据。代码与业务规则冲突时，应先修正规则状态，再修改实现。

规则来源必须登记在 `RULE_SOURCE_LEDGER.md`，不能只留在聊天上下文中。

### 2.2 业务状态

| 状态 | 含义 | 是否可以自动执行 |
| --- | --- | --- |
| 已确认 | 规则含义、取值和适用范围已确认 | 可以进入实现 |
| 暂定 | 当前可以用于讨论或测试，但仍需最终确认 | 不可用于无人值守真实订单 |
| 待确认 | 存在明确问题，等待业务回答 | 不可以 |
| 待样本 | 有流程描述，但缺少原始数据样本 | 不可以 |
| 暂缓 | 已决定不进入第一版 | 不可以 |
| 不适用 | 已确认该来源不使用此规则 | 可以跳过 |

### 2.3 实现状态

业务状态和实现状态分开记录。业务确认不代表已经写入系统，代码存在也不代表规则已经确认。

| 状态 | 含义 |
| --- | --- |
| 未接入 | 尚未写入机器配置或代码 |
| 已接入 | 已有可核验的配置或代码 |
| 部分接入 | 只实现了一部分 |
| 待验收 | 已实现，但还没有用真实流程完成验证 |
| 已验收 | 已按样本和真实页面完成验证 |

## 3. 系统流程和模块边界

```text
员工上传原始Excel，或来源连接器取得订单
        ↓
1. 文件检查与来源识别
        ↓
2. 来源解析器提取客观事实
        ↓
3. 统一订单模型 ParsedOrder
        ↓
4. 显式路由到目标平台
        ↓
5. 商品映射 + 平台业务规则
        ↓
6. 业务规则覆盖门禁
        ↓
7. 管易订单草稿与字段校验
        ↓
8. 生成管易自定义订单导入Excel
        ↓
9. 单文件上传前预检
        ↓
10. 多文件时：全部通过后按输入顺序合并并再次预检
        ↓
11. 管易登录、导航、文件选择和提交
        ↓
12. 任务中心核验、订单审核和后续发货
```

### 3.1 来源识别器

负责判断文件属于哪家公司、哪种订单类型。它不生成管易字段。

只有高置信度且唯一匹配时才自动继续。无法唯一判断时，Agent 必须追问。

### 3.2 来源解析器

每种原始Excel拥有独立解析器。解析器只读取来源事实，不决定管易店铺、仓库、物流或商品编码。

### 3.3 统一订单模型

统一订单模型是固定的数据合同，不是员工使用的Excel模板。

所有来源使用相同的基础结构：

- 来源公司、文件、工作表、原始行号和来源订单号。
- 收件人、联系方式和地址。
- 原商品编码、原商品名称、规格、数量和单位。
- 来源提供的时间、金额、原始备注和物流事实。
- `source_extensions`：需要保留、但还不适合进入公共字段的来源特有事实。

统一订单模型不保存：

- 管易店铺、仓库和支付方式。
- 管易商品代码和规格代码。
- 管易平台单号生成结果。
- 管易物流选择结果。
- 管易卖家备注生成结果。
- 是否允许上传、审核或发货。

判断标准：描述“原订单本来是什么”的信息进入统一模型；描述“进入管易后应该填什么”的信息进入管易平台规则和草稿。

### 3.4 商品映射模块

商品映射独立于来源解析器和Excel渲染器。

基本原则：

- 来源明确提供稳定商品编码时，优先按已确认的精确编码映射。
- 只有商品名称时，可以由AI或规则产生候选，但不得自动确认。
- 候选必须由用户确认后才能用于本次真实订单。
- 一次性确认默认只影响本次运行。需要以后复用时，应单独写入版本化映射配置。
- 未确认映射必须阻断生成“可上传”文件。

### 3.5 管易平台规则模块

负责生成店铺、平台单号、买家会员、仓库、支付、物流和卖家备注等管易字段。

每个来源可以拥有自己的规则包。规则包不写入统一模型，也不写死在Excel渲染器中。

### 3.6 Excel渲染器

渲染器只把已经确定且校验通过的管易订单草稿写入官方模板，不进行业务推理。

### 3.7 浏览器执行器

浏览器执行器只负责管易登录、页面导航、表单设置、文件选择、提交和结果核验。它不解析公司Excel，也不决定商品映射和物流规则。

### 3.8 多文件批次编排器

当用户一次提供多个原始 Excel 时，默认生成一个合并后的管易 Excel；只有用户明确要求分开或分别输出时才生成多个文件。批次编排器复用单文件完整链路，不拥有公司业务规则。每份原始 Excel 必须先独立识别、转换并通过预检；全部文件进入同一平台模板且没有重复文件或跨文件平台单号冲突时，才按用户提供顺序合并成一个管易 Excel，并对合并结果再次预检。

任一文件需要追问时整批不出表；不得交付已经通过的部分文件作为半批次，也不得为凑批次而跳过来源识别、商品映射或规则门禁。

### 5.6 玉米入仓订单

样本文件：`玉米入仓订单20260920(1).xlsx`

样本内容更接近采购订单，主要包含商品、订货数量、结算价、金额和统一收货地点，不包含面向消费者逐单发货所需的订单集合。

运行规则：

1. 识别到该类文件后，不直接生成发货订单。
2. Agent先询问：“这是采购入仓资料，还是需要给收件人发货的订单？”
3. 用户确认采购入仓时，本文件退出发货链路。
4. 用户确认需要发货时，再要求补充逐单收件人、联系方式、地址和订单对应关系。

状态：已确认追问策略；不属于当前自动发货来源。

### 6.9 物流

当前业务答复明确了优先级：

1. 原始订单明确指定物流时，客户指定物流优先级最高。
2. 原始订单没有指定物流时，才执行尚舆默认物流规则。

- 8根装购买数量达到2袋及以上，使用中通快递（重货）。
- 10根礼盒装使用中通快递（重货）。
- 其他情况默认韵达快递。

这不能归纳成“玉米总根数大于等于10就一定走重货”。当前版本仅执行已经明确的包装条件；底层重量公式仍作为后续可替换策略。

后续优化问题，不阻塞当前恬田MVP：

1. 向ROY确认准确的重量公式和中通重货阈值。
2. 建立包含单品净重、包装重和计费规则的商品重量资料。
3. 一张订单多个商品时，是否按整单总重量计算；从物流是订单级字段看应按整单，但仍需业务确认。
4. 10根礼盒、8根装2袋之外的组合如何计算，不能只靠根数猜测。
5. 重量规则适用于哪些来源和哪些商品类别。

- 输出商品行数与统一模型商品数量能够对账。
- 不存在未确认的适用业务规则。

manifest只证明文件通过预检，不代表用户授权上传。

多文件批次还必须检查：

- 原始文件SHA-256不能重复。
- 每个单文件暂存成品与自身manifest哈希一致。
- 所有文件的目标平台与目标模板配置一致。
- 同一订单可以在一个原始文件中占多行，但同一平台单号不得同时来自两个不同原始文件。
- 合并后的订单数、商品行数和平台单号一致性重新通过完整预检。

## 8. 上传后与后续流程

### 8.1 任务中心核验

提交前保存任务中心基线。提交后只有出现唯一新增、且页面行和数据模型ID一致的导入任务，才能关联到本次操作。

如果出现多个新增任务、任务ID证据不足或页面状态不明，系统停止并要求人工确认，不重复提交。

当前状态：任务中心只读和唯一新增任务核验已实现；尚未与真实“确定”提交完成端到端验收。

### 8.2 订单审核

PDF要求导入后在订单查询中找到待审核订单，再执行审核。

当前边界：

- 第一版真实导入测试只生成待审核订单。
- 自动审核尚未获得独立权限，也尚未实现。
- 导入成功不等于审核成功，更不等于已经发货。

### 8.3 百礼汇物流回填

管易产生物流后，在百礼汇代发订单中新增包裹，选择快递并填写物流单号。

该能力属于 `post_fulfillment` 独立模块，不与取单、转换和管易上传绑在同一个写入动作中。第一版暂缓。

## 9. 追问与停止规则

出现以下任一情况，Agent必须停止当前转换或上传，并提出具体问题：

1. 文件无法唯一识别来源公司或订单类型。
2. Excel本身没有平台标识，用户也没有提供平台或订单类型提示。
3. 文件用途不清楚，例如采购入仓和消费者发货无法区分。
4. 缺少收件人、联系方式、完整地址或商品数量。
5. 原始字段在同一订单内相互冲突。
6. 商品映射没有精确命中，或命中多个候选。
7. 适用的店铺、平台单号、物流或备注规则尚未确认。
8. 当前页面与已登记页面结构不一致。
9. 出现未知弹窗、布局不稳定或任务中心无法唯一核验。
10. 写请求可能已经发出，但业务结果无法确认。

追问必须说明：

- 哪个文件、工作表、订单或商品出现问题。
- 缺少或冲突的具体信息。
- 为什么该信息会影响结果。
- 用户可以如何回答或补充资料。

不得使用临时默认值绕过阻断规则。

## 10. 浏览器自动化安全规则

- 使用专用持久浏览器会话，不依赖员工日常浏览器窗口。
- 登录会话优先复用；凭证只保存在系统安全凭证提供器中，不写入Skill、源码或普通配置。
- 需要短信验证码时，由执行器先点击“获取验证码”，关闭已知提示后再向用户索取本次验证码。
- 页面跳转、重载、新页面和弹窗后重新检查浏览器几何。
- 优先使用稳定Locator；坐标只作为最后手段，并且动作前即时测量、动作后回读业务状态。
- 截图不得改变业务页面viewport、缩放或滚动位置。
- 写入前可以恢复页面；写请求发出或可能发出后，禁止盲目重试，必须先查重和核验。
- 点击成功、Toast出现或文件输入变化都不能单独证明业务成功。
- 未知弹窗、未知页面、几何异常或任务ID不唯一时采用fail-close。

## 13. 规则确认和接入计划

### 13.1 规则讨论顺序

1. 先确认来源和路由：哪些文件属于哪个公司，进入哪个平台。
2. 再确认统一模型：每个来源事实落在哪个标准字段或扩展字段。
3. 再确认管易规则：店铺、平台单号、买家会员、金额、仓库、商品、物流和备注。
4. 再确认上传规则：页面选项、提交授权、任务中心核验和审核边界。
5. 最后确认百礼汇等独立后续流程。

### 13.2 冻结条件

V1.0冻结前必须满足：

- 当前第一版来源范围已经明确。
- 每个第一版来源都有样本、识别规则和目标路由。
- 所有适用业务规则具有明确状态。
- 不再使用“可能”“一般”“大概”等无法执行的表述。
- 商品映射和规则修改的确认、版本和回滚方式已经确定。
- 待确认规则会阻断真实输出，而不是填入默认值。

### 13.3 接入原则

规则冻结后再执行：

```text
人类可读规则文档
    ↓
机器可读规则目录和来源规则包
    ↓
确定性程序实现
    ↓
单元测试与样本回归测试
    ↓
生成文件人工审核
    ↓
夜间受控真实上传测试
```

每条机器规则必须能够追溯到规则编号、证据、确认日期和实现引用。不得只在模板渲染器或浏览器脚本中增加临时条件。

规则来源台账属于冻结材料的一部分。没有稳定来源ID、文件指纹或决策记录的规则，不能进入V1.0。
