# 尚舆订单转换 Skill 架构

状态：恬田、SAM、NDD、自营文字单和荣之达文字单的管易Excel转换链路已实现；自动上传仍受独立门禁控制。

业务规则讨论稿见 [ORDER_AUTOMATION_RULES_V0.1.md](ORDER_AUTOMATION_RULES_V0.1.md)，完整规则判断流程见 [RULE_DECISION_FLOW_V0.1.md](RULE_DECISION_FLOW_V0.1.md)，规则的唯一权威结构见 [RULE_MODULE_STRUCTURE.md](RULE_MODULE_STRUCTURE.md)，规则来源和证据追溯见 [RULE_SOURCE_LEDGER.md](RULE_SOURCE_LEDGER.md)。架构文档不替代业务规则和来源台账。

## 1. 目标与边界

这个项目最终以一个 Agent Skill 入口提供给员工使用。普通来源由员工把原始 Excel 交给 Agent；百礼汇来源由独立连接器从其专用后台取得订单。两类来源都由 Skill 调用确定性脚本完成识别、路由、转换和校验，再由 Agent 返回可以上传的平台文件。

第一版不建设网页上传入口、用户系统、数据库或长期订单中心。Agent 已经负责文件接收与结果交付。转换过程默认不登录平台、不上传订单，也不长期保存收件人信息。

## 2. 运行主流程

```text
Agent 接收一个或多个 Excel，或调用已授权的后台来源连接器
        |
        v
来源检查与识别
        |
        v
是否命中已登记模板？-- 是 --> 确定性来源适配器（脚本快线）
        |
       否
        |
        v
用户是否明确公司？-- 否 --> Agent追问公司和用途
        |
       是
        |
        v
无数据值结构探针 -> 一次性自适应字段计划 -> 必要信息追问
        |
        v
信息是否足够？-- 否 --> Agent 提出具体问题并等待回答
        |
       是
        |
        v
公司库：确认稳定公司ID、来源归属和已启用工作流
        |
        v
路由解析：来源配置 -> 目标平台流程
        |
        v
确定性文件适配器、自适应计划解析器或后台连接器 -> 最小中间订单 ParsedOrder
        |
        v
目标平台包
  - 已确认组合商品展开
  - 平台商品映射
  - 平台业务规则
  - 平台字段校验
  - 官方模板渲染
        |
        v
管易可上传 Excel + 非敏感处理报告
        |
        v
Agent 返回结果；识别、用途或字段不确定时停止并追问
```

识别和路由发生在平台规则之前。公司身份与Excel格式分别处理：公司决定复用哪个已确认业务工作流，文件格式只决定如何抽取来源事实。平台商品编码、店铺、仓库、支付方式、平台单号生成方式和模板列都不进入公共中间模型。

## 3. 模块边界

### 3.1 Skill 调度层

职责：

- 找到用户提供的 Excel 文件。
- 调用统一转换命令。
- 在识别不确定或规则缺失时向用户说明问题。
- 返回生成文件和简短结果。

不负责：

- 临场推断订单字段值。
- 在 `SKILL.md` 中保存公司业务规则。
- 未经明确授权登录或提交平台。

### 3.2 工作簿检查与来源识别

输入：本地 Excel 文件路径。

检查：

- 文件类型和工作簿是否可读。
- 工作表名称。
- 表头所在行与表头集合。
- 必需列、可选列和稳定特征。
- 格式指纹与公司指纹分别判断；通用表头不能单独证明公司身份。
- 未登记的新列进入 `schema_warnings`，必需列缺失继续阻断。
- 是否同时匹配多个来源配置。

输出 `DetectionResult`：

```json
{
  "source_profile_id": "tiantian_warehouse_v2",
  "source_label": "恬田代发仓",
  "order_type": "warehouse_order",
  "confidence": "high",
  "matched_features": ["sheet:仓库订单", "header:来源单号", "company_column:仓库订单!渠道名称"],
  "schema_warnings": [],
  "issues": []
}
```

规则：

- `high` 才允许自动继续。
- `medium` 或多个配置并列时，Agent 必须让用户确认。
- `low` 或没有匹配时停止，不选择最相似的配置继续转换。
- 用户明确提供公司且文件命中该公司的已登记模板时走脚本快线。
- 用户明确提供公司但没有命中已登记模板时进入自适应通道，不再把固定模板ID当作公司ID强行校验。
- 只有格式匹配、没有公司字段或稳定位置证据时返回 `COMPANY_IDENTITY_UNCONFIRMED`。

### 3.2.1 自适应来源通道

自适应通道只服务于公司库中已经登记、并且已有可运行目标工作流的公司。它不创造新的公司规则，也不直接生成平台Excel。

流程：

1. 结构探针读取工作表、候选表头、列字母、非空数量和数据类型；不返回任何数据行值。
2. Agent或确定性别名表生成一次性字段计划，把来源列映射到`ParsedOrder`字段。
3. 计划绑定来源文件SHA-256、表头签名、公司ID和复用的业务规则来源配置；任一变化都重新分析。
4. 原表缺少商品、数量或来源单号时返回批次级追问；用户确认后才允许写入批次默认值或日期顺序号。
5. 自适应解析器重新读取原文件并生成`ParsedOrder`，之后复用原公司的路由、SOP门禁、商品映射、平台规则和预检。
6. 一次性计划不自动成为永久规则。经员工核对和真实导入验收后，才能将其字段映射提升为版本化来源配置，使后续相同格式回到脚本快线。

计划合同位于`contracts/adaptive_source_plan.schema.json`。计划只保存列映射、结构签名和经确认的批次默认值，不保存姓名、电话、地址或订单数据行。

### 3.3 追问与补充信息

识别到文件但无法确定用途，或者订单缺少生成平台文件所需的信息时，不应直接排除文件，也不应填入猜测值。模块返回 `ClarificationRequest`，由 Agent 向用户提出具体问题。

典型例子：

```json
{
  "code": "ORDER_PURPOSE_UNCLEAR",
  "scope": "batch",
  "source_ref": "玉米入仓订单20260920.xlsx/Sheet1",
  "question": "这份文件是采购入仓单，还是需要给收件人发货的订单？",
  "reason": "文件包含商品和订货数量，但没有收件人、联系方式和收货地址。",
  "answer_type": "single_choice",
  "choices": ["采购入仓，不生成发货订单", "需要发货，我将补充收件信息"],
  "blocking": true
}
```

处理规则：

- 先问决定后续流程的批次级问题，不要立即逐行追问缺失字段。
- 如果用户确认是采购或入库资料，将文件标记为非发货输入并结束该文件处理。
- 如果用户确认需要发货，再请求包含收件人、联系方式、地址和订单对应关系的补充文件或信息。
- 回答只作为本次运行的临时补充；若要成为以后自动执行的稳定规则，必须另行更新版本化配置。
- 追问没有得到回答前，不生成标记为可上传的平台文件。

请求合同位于 `contracts/clarification_request.schema.json`。

### 3.4 路由解析

输入：`source_profile_id + order_type`。

输出 `RouteDecision`：

```json
{
  "route_id": "tiantian_warehouse_to_guanyi_v2",
  "target_platform": "guanyi",
  "target_profile_id": "guanyi_order_import_v1",
  "post_fulfillment_profile_id": null
}
```

路由是显式配置，不由 AI 每次重新判断。当前机器可读草案位于 `config/routing/order_routes_v1.json`。

### 3.4.1 公司注册库

公司库位于 `config/companies/company_registry_v1.json`，是各模块上方的轻量总索引。它解决“这个来源格式属于哪个公司、公司的法定名称与简称是什么、公司允许走哪些已登记工作流、目前能力做到哪一步”，但不保存店铺、物流或商品等业务值。

公司库保存：

- 稳定 `company_id`、法定名称、显示名、简称和别名。
- 该公司拥有的一个或多个来源配置。
- 来源配置到路由、目标平台规则和商品映射空间的引用。
- 转换、上传等能力的阶段状态和是否允许运行。
- 来源文档引用和最后核验日期。

公司库不保存：

- Excel列名与识别证据；这些留在 `source_profiles`。
- 字段转换、店铺、物流、备注和平台单号；这些留在 `platform_rules`。
- 商品编码对应关系；这些留在 `catalog`。
- 页面导航与写入权限；这些留在浏览器执行器。

公司法定名称与简称都可以作为公司身份提示；大小写不敏感的简称会先解析成稳定`company_id`。平台规则必须显式声明`prefix_source=company_abbreviation`或相应会员前缀引用，简称才会进入输出字段，避免所有公司被强制套用同一种单号格式。

转换服务会强制执行双向归属与工作流引用校验。公司未登记、一个来源同时归属多个公司、公司库与路由引用不一致、工作流未启用时均停止，不继续猜测。只有名称和简称、没有来源模板与规则的公司使用`identity_only`状态；它们可以被识别，但不能转换。`audit-companies` 可在不读取订单数据的情况下检查全部引用。

### 3.4.2 共享平台策略模块

管易跨公司的同类业务值不再复制到每个公司规则包。`config/platform_rules/guanyi/policy_modules_v1.json`是共享店铺、普通买家会员、公共默认值、物流、备注分流和卖家备注组合策略的唯一可执行权威；公司规则包通过`policy_module_refs`引用，并只保存公司专属的单号、字段显示、套餐和显式例外。给快递员的配送指令由共享备注分流模块追加到收货地址末尾，非快递员备注再进入卖家备注组合模块。

加载规则时先解析共享模块，再执行SOP覆盖门禁和转换。引用缺失、模块目标类型不匹配、覆盖格式错误，或同一个规则既内联又引用时全部fail-close。公司库审计也会验证所有活动工作流的模块引用。

### 3.5 来源适配器与后台连接器

两者职责相同：

- 读取指定来源格式，或从已确认的后台接口取得订单。
- 识别一单多行并正确分组。
- 提取订单的客观事实。
- 保留原文件、工作表和行号追踪信息。
- 信息完整时输出 `ParsedOrder`；信息不足时输出 `ClarificationRequest`。

不负责：

- 决定目标平台。
- 生成平台单号。
- 选择平台店铺或仓库。
- 解析管易商品代码。
- 写入平台模板。

来源模块分为两类：

- 文件适配器：员工上传公司原始 Excel 后识别和解析。
- 后台连接器：在运行时授权范围内通过后台导出、官方 API 或已登录网页读取订单。

无论来源形式如何，输出都必须满足同一个 `ParsedOrder` 合同。账号、密码和会话信息不得写入 Skill、配置或处理报告。

### 3.6 最小中间订单

`ParsedOrder` 是来源适配器与平台包之间的稳定合同，正式草案位于 `contracts/parsed_order.schema.json`。

它只保存来源中的客观事实：

- 来源文件、工作表和行号。
- 来源公司、文件类型和来源订单号。
- 收件人、联系方式和地址。
- 来源商品、规格、数量和单位。
- 下单时间、金额和原始备注等可选事实。

它不包含：

- 管易店铺、仓库和支付方式。
- 管易商品代码或规格代码。
- 百礼汇平台字段。
- 平台单号生成结果。
- 是否可以上传等平台校验状态。

平台新增字段时先判断它是不是所有来源都可能提供的客观事实。只有满足这个条件才扩展 `ParsedOrder`；否则字段属于对应平台草稿模型。

### 3.7 目标平台包

每个平台包拥有自己的完整转换逻辑：

```text
ParsedOrder
  -> 来源组合商品展开（如适用）
  -> 平台商品解析
  -> 平台业务规则补全
  -> PlatformOrderDraft
  -> 平台校验
  -> 官方模板渲染
```

平台包内部至少分为：

- 商品映射：来源商品标识到该平台商品/规格编码。
- 组合商品展开：只对已确认的来源商品与规格执行一对多拆分，记录每个目标商品和数量倍数；未命中则继续普通一对一映射。
- 店铺路由：使用已确认的精确商品编码、订单类型或显式来源证据分配店铺；未命中或一单多店铺时阻断并追问。
- 业务规则：平台单号、仓库、状态、支付和物流等。
- 草稿模型：该平台需要的字段集合。
- 校验器：阻断缺字段、未知商品、重复单号和模板不兼容。
- 渲染器：复制官方模板后写入数据，保留工作表名称、格式和文本标识符。

#### 管易平台包

第一版统一使用管易“自定义订单导入”单文件模板，与 SOP 中 SAM 订单的自定义导入方式一致。模板包含 48 列；同一订单有多件商品时，每件商品占一行，并重复相同平台单号及订单级字段。

管易允许自定义导入增删列并调整列位置；系统仍使用已校验的官方48列模板作为稳定合同。人工文件中的“团标题”等非业务列不进入自动输出。

模板用红色表头标出的必填列是：店铺、平台单号、买家会员、支付金额、商品代码、数量、价格、收货人和收货地址。

当前模板结构已记录在 `config/platform_profiles/guanyi_order_import_v1.json`。

#### 百礼汇来源连接器

百礼汇不是订单导入目标平台，而是一个特殊订单来源。已确认的主流程是：

```text
百礼汇专用后台取单
  -> 百礼汇来源连接器
  -> ParsedOrder
  -> 百礼汇来源对应的管易商品映射与业务规则
  -> 管易自定义订单导入.xlsx
```

员工仍然只使用同一个 Skill 入口。百礼汇只替换来源模块，后面的中间合同、商品映射校验、管易规则和模板渲染全部复用。

当前还需要确认后台的实际取单方式：优先使用后台 Excel 导出，其次是官方 API；只有前两者不可用时，才在用户已登录且明确授权的会话中读取网页。相关配置位于 `config/source_connectors/bailihui_backend_v1.json`，系统能力边界记录在 `config/platform_profiles/bailihui_v1.json`。

管易产生物流后的百礼汇发货回填是另一项独立能力，不与“取单并导入管易”绑在同一个模块中；待入单闭环稳定后再实现。

### 3.8 转换服务与结果

统一转换服务负责编排模块，但不包含公司或平台业务规则。

成功时返回：

```json
{
  "status": "ready",
  "source_profile_id": "tiantian_warehouse_v2",
  "target_profile_id": "guanyi_order_import_v1",
  "order_count": 7,
  "outputs": ["管易自定义订单导入.xlsx"],
  "issues": []
}
```

阻断时不生成伪装成可上传的文件，返回具体错误、来源工作表和行号。

### 3.9 上传前预检与批次清单

管易 Excel 渲染完成后必须再次从磁盘读取并执行上传前预检。预检属于平台包，不属于浏览器执行器，检查：

- 工作表和 48 列表头与登记模板一致。
- 至少存在一行订单明细，必填列不为空。
- 数量、金额和 0/1 标志符合类型与范围。
- 标识符列保持文本格式。
- 不包含公式或错误单元格。
- 同一平台单号的订单级字段一致。

通过后生成符合 `contracts/upload_batch.schema.json` 的 manifest。manifest 只包含文件哈希、大小、配置版本、订单数、明细行数、检查结果和非敏感错误位置，不包含姓名、手机号或地址，也不构成上传授权。

浏览器执行器在打开文件选择器之前必须重新计算 Excel 哈希并与 manifest 比对。manifest 缺失、状态不是 `ready`、路径或哈希不一致时停止。即使 manifest 通过，文件选择和上传仍属于后续独立能力，需要单独的运行时授权。

### 3.10 多文件批次编排

批次编排层位于单文件转换服务之上，不复制任何公司或平台规则。统一入口收到多个原始 Excel 时默认进入合并模式；只有用户明确要求分开或分别输出时才进入单文件循环模式。合并模式依次对每个文件运行完整的“识别 → 公司库 → 路由 → 解析 → 商品映射 → 平台规则 → 渲染 → 预检”链路；单文件中间成品只写入临时目录。

只有同时满足以下条件时，批次层才把已验证的数据行按用户提供文件的顺序重新渲染成一个正式 Excel：

- 每个文件的状态均为 `ready`。
- 所有文件进入同一目标平台和同一目标模板配置。
- 原始文件内容哈希不重复。
- 不同文件之间没有相同的平台单号。
- 每个暂存 Excel 的 SHA-256 与自身预检 manifest 一致。

任一文件需要追问时，整批返回 `needs_input`，不生成部分 Excel；任一文件失败、哈希异常或跨文件单号冲突时，整批返回 `blocked`。成功批次只交付一个合并 Excel、一个对应 manifest 和一个不含收件信息的批次报告。批次合并不会改变单文件的来源判断、商品映射或业务规则。

## 4. 商品映射

商品映射采用公司隔离的多标识级联匹配，但由目标平台包调用：

```text
来源配置 + 标识类型 + 来源编码/名称
        -> 内部商品标识
        -> 目标平台商品代码与规格代码
```

内部商品标识只表示同一个真实商品，不保存平台业务含义。同一商品在管易和百礼汇可以映射为不同编码。

确定性优先级为：公司专属已确认编码、已确认名称别名、标准化后唯一精确的管易商品名称。名称同时命中多个规格、模糊相似或未匹配时阻断并追问。来源编码与管易编码相同也不能自动直连，除非该来源配置明确声明两个编码空间相同。

来源匹配政策和身份保护随 Skill 版本发布；一对一商品目标映射以飞书正式映射表为权威数据源。日常转换只自动加载最近一次成功同步的正式快照，不再自动加载本机旧映射。一次性调试覆盖只能显式传入，不能成为员工正常入口的隐式状态。

组合商品展开不是普通商品映射。它由独立规则包维护“来源商品+来源规格 -> 多个目标商品+数量倍数”，展开后每个目标商品仍必须通过管易商品主档精确校验。禁止向普通一对一映射表写入相同来源键的多个目标商品，否则必须按冲突处理。

### 4.1 飞书共享映射治理

共享映射采用两个飞书电子表格工作簿：正式映射是只读权威数据源，待确认映射是非可信提案收件箱。普通Agent不得直接修改正式映射。

待确认工作簿按当前飞书`user_id`自动路由到个人Sheet。路由表由Agent自动创建和修复；路由表缺失时通过个人Sheet的`owner_user_id`元数据重建。没有Sheet时复制模板创建；同一用户出现多个Sheet时阻断，不自动合并或删除。

飞书工具通过`FeishuSheetGateway`适配层接入，优先使用Agent原生能力，CLI只作备用。待确认写入要求用户身份、确定性`mapping_key`、幂等`proposal_id`和写后精确回读。所有者发布器在独立模块中完成全局查重、商品主档与公司来源校验、冲突整批阻断、两阶段失败关闭、正式版本递增、发布日志和待确认状态回写；普通转换器没有正式表写权限。详细合同见`docs/FEISHU_MAPPING_GOVERNANCE.md`。

## 5. 校验分层

### 来源校验

- 工作簿可读。
- 必需工作表和表头存在。
- 一单多行的订单级字段一致。
- 数量是正数。
- 联系方式和地址没有明显缺失。

### 中间合同校验

- `ParsedOrder` 满足 JSON Schema。
- 每个订单有稳定的 `record_key` 和来源追踪信息。
- 不允许混入平台专属字段。

### 平台校验

- 平台必填字段齐全。
- 商品和规格映射已确认。
- 平台单号规则已确认且批次内不重复。
- 模板版本与平台配置一致。
- 同一订单的多行商品使用相同平台单号。
- 每个中间订单至少产生一行模板记录，模板记录数量等于全部商品明细数量。

### SOP业务规则覆盖门禁

平台字段校验只能发现“值缺失”，无法发现“SOP规则从未进入系统”。因此在商品映射和模板渲染前增加独立覆盖门禁：

- 规则目录保存稳定规则ID、来源页、模块归属和执行阶段。
- 每个来源到平台的规则包声明适用规则的状态与实现引用。
- 规则包先通过轻量核心Schema；公司新增业务字段不受限制，但身份、版本和覆盖声明不能缺失或写错类型。
- 标记为`implemented`的引用必须同时存在于实现注册表，并指向可加载代码入口和测试文件。
- `implemented` 和 `not_applicable` 必须经过确认；其他状态一律阻断对应阶段。
- 转换、上传、上传后核验和履约回填分阶段检查，避免转换阶段规则与浏览器权限耦合。
- 规则包漏掉目录要求的规则时直接返回结构化追问，不允许静默生成文件。

当前转换服务已强制执行 `conversion` 阶段；`upload` 阶段将在启用“确定”提交前接入浏览器执行器。详见 `docs/BUSINESS_RULE_COVERAGE.md`。

## 6. AI 与脚本的职责

脚本承担：

- 表头识别和确定性评分。
- 来源字段解析和订单分组。
- 路由查表。
- 商品映射、业务规则和校验。
- 平台模板写入。

Agent/AI 承担：

- 理解员工请求并选择本 Skill。
- 发现识别结果不唯一时组织人工确认。
- 解释阻断原因。
- 调用脚本并返回结果。

AI 的一次确认不能只对当前文件生效后被遗忘。确认后的稳定规则应写入新的版本化配置或适配器，并通过样本测试。

## 7. 记录与隐私

第一版不建设持久化治理系统。每次运行只产生一个非敏感处理摘要，包含：

- 输入文件名和文件指纹。
- 识别到的来源配置。
- 使用的路由和平台配置版本。
- 成功、阻断订单数量。
- 错误代码及来源行号。
- 输出文件名。
- 用户对本次运行追问的回答类型，但不记录回答中的个人信息。

处理摘要不保存姓名、手机号和详细地址。中间订单默认只在运行期间存在；除非用户明确要求调试，不落盘保存包含个人信息的中间 JSON。
