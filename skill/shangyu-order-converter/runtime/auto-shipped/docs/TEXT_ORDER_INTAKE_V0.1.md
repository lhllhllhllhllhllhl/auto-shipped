# 文字订单入口设计 V0.1

## 目标

支持员工直接提交聊天文字、截图或复制地址单，同时保持现有“公司识别 → 平台路由 → 商品映射 → 业务规则 → 管易Excel → 预检”链路不变。

## 模块边界

- 路由先尝试已登记固定来源；固定来源不命中时，只有公司库明确标记`fallback_enabled`的公司才可按公司简称进入`generic_company_manual_v1`。未登记公司或别名多义仍追问。
- 通用兜底缺少订单编号和来源单号时，使用“公司简称+YYYYMMDD+飞书中央日序号”；第二天按新日期从001开始，不同简称互不污染，同一来源重跑复用原号段。
- 通用兜底店铺不靠公司名硬编码：先按稳定`company_id`查SKU—店铺正式关系，再查`manual_all`；共享来源配置不参与店铺作用域。仍未命中时，已映射玉米回退“光明满元气”，非玉米回退“淘橘子”并在生成Excel后的结果小节告知；混合店铺停止追问。

1. `Agent提取层`：读取文字或截图，按订单分段，保留必填`source_item_text`，并生成带字段来源状态和受控不确定项代码的草稿；Agent不拥有公司/profile、单号策略或追问文案的决定权。
2. `文字草稿门禁`：默认按已登记渠道确定性路由，校验显式来源与渠道兼容性，再校验订单身份、收件信息、商品、规格、数量、单位、联系方式和字段来源；仅输出脱敏预览、路由证据与程序生成的集中追问。预览同时说明“订单编号 > 来源单号 > 已登记自动生成规则”的实际编号路径。
3. `用户确认门禁`：普通核对延后到最终`preview_ready`Excel之后，与唯一商品候选在同一轮集中确认；关键缺失或歧义仍在准备阶段阻断。
4. `标准化输入层`：把草稿写为临时标准化Excel，并生成与文件SHA-256绑定的一次性自适应字段计划；临时商品映射另用规范化订单事实SHA-256绑定，避免同内容Excel重生成导致失效。
5. `现有转换总控`：继续负责公司路由、正式商品映射、套餐展开、店铺、单号、物流、备注、管易模板和上传前预检。

文字入口不维护第二套商品和物流规则。AI只负责从非结构化内容提出候选；可执行结论仍由脚本和版本化规则决定。

## 安全规则

- 原始文字或OCR全文不写入规则库、Skill、处理报告或聊天回复。
- 草稿和标准化Excel含收件信息，只保存在本次任务目录，并按订单源文件同等级保护。
- 对平台、订单号、联系方式、地址、商品或数量的推断必须标记为`inferred`并阻断。
- 用户未明确指定固定流程时，草稿必须使用`registered_manual_channels + deterministic_router`，公司/profile为null且不提供单号策略。用户明确指定时使用`single_profile + user_explicit`，但渠道不兼容仍必须返回唯一来源冲突问题。
- `uncertainties`只允许Schema登记的代码、字段和理由；程序忽略Agent自写问题。正式商品映射缺失由商品解析层在读取权威映射后统一追问。
- 用户确认文字识别结果不等于确认商品映射或业务规则；后续转换仍可继续追问。
- 收件信息只在最终预览中进行一次批次级核对；预览决策载荷继续携带不保存完整隐私值的`masked_order_preview`，员工当前订单处理对话可从本次草稿展示完整值。程序先生成完整预览Excel，回复先展示集中确认小节，最后在“待确认 Excel”小节附文件链接，不能先问后生成表。普通聊天文字与截图/OCR都适用；已知固定模板Excel不进入该核对。
- 用户只确认候选正确但没有选择复用范围时，先按仅本次交付成品；成功结果用`mapping_reuse_bundle`非阻断询问是否以后沿用，不回复即保持仅本次。
- 没有公司级证据时必须询问公司。天猫、京东、淘宝等是渠道标签，不能单独决定公司规则。
- 来源单号缺失时不得随意生成。通用日期顺序号必须由用户确认具体参数并使用专用确认口令；已登记公司的固定生成规则由版本化来源配置执行。
- Agent保留商品原文并尽量拆成品牌、商品主体、规格、数量和单位，不能让模型直接选择管易代码。确定性规范化模块把不同字段边界整理成统一的`品牌+商品主体+规格`身份；数量和单位保持独立，未知附加规格不得丢弃。当前来源或全局正式名称映射的规范身份唯一相同时可自动命中，跨来源同身份仍只给待确认候选，模糊或多候选仍追问。

## 当前范围

V0.1已实现草稿合同、脱敏校验、集中追问、用户确认门禁、标准化Excel与一次性计划生成。文字草稿可分别保留订单编号和来源单号，统一优先使用订单编号；两者均无时才调用来源已确认的飞书中央日序号规则，并在确认预览中直接说明规则，不再反问用户是否补号。2026-10-15起所有新平台单号保留基础业务单号，不再追加机器人尾缀`A`。已登记公司或业务来源可以继续进入现有转换链路。商品字段采用“AI保留原文并初拆Schema + 确定性短语规范化 + 正式映射校验”；字段边界不同但语义身份一致时可以稳定复用正式名称映射，这不是模糊匹配。尚舆自营天猫/京东文字玉米单按渠道分配旗舰店；自营“袋”匹配8棒家庭装，“根”尚未登记时追问；自营“京东中通”表示京东旗舰店订单且物流字段原样填写`京东中通`。淘橘子淘宝/KQYD日用品文字单在缺少两类订单标识时分别使用`TB`/`KQYD`+`YYYYMMDD`+最少三位飞书中央日序号，未指定物流默认韵达。RZD同样只在两类订单标识均缺失时生成中央日序号。JZDZ/DRJY作为员工可见的独立手工来源，缺号时分别生成`JZDZ`/`DRJY`+`YYYYMMDD`+最少三位飞书中央日序号，商品映射后再由正式SKU—店铺关系选择店铺。裸棒在普通发货中禁用。

2026-11-02收紧混合手工订单入口：普通文字/截图草稿即使被Agent抢填公司或profile，也仍由`deterministic_router`按每笔渠道标记重新路由，并返回`routing_evidence`。只有`user_explicit`单一来源模式可以保留用户指定流程；渠道不兼容时返回`TEXT_ORDER_PROFILE_CHANNEL_MISMATCH`且不进入商品、店铺或单号追问。高置信商品尾部结构可确定性拆分，例如`滑溜 m号3双`规范为`滑溜 / M / 3 / 双`。
